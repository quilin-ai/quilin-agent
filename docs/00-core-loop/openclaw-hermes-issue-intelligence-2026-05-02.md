# OpenClaw 与 Hermes 未解决 Issue 情报 / OpenClaw and Hermes Unresolved Issue Intelligence

## 范围与方法 / Scope and Method

This note refreshes unresolved, high-signal GitHub issue themes for `openclaw/openclaw` and `NousResearch/hermes-agent` on 2026-05-02 Asia/Shanghai time. I used live GitHub issue data for open issues, combining the newest 100 open issues per repository with the 30 most-commented open issues per repository. GitHub search reported 3,461 open OpenClaw issues and 2,768 open Hermes issues at collection time, so this note is a theme intelligence slice rather than a full ticket inventory.

本记录在北京时间 2026-05-02 刷新 `openclaw/openclaw` 与 `NousResearch/hermes-agent` 的未解决高信号 GitHub issue 主题。我使用实时 GitHub open issue 数据，每个仓库结合最新 100 个 open issue 与评论数最高的 30 个 open issue。采集时 GitHub search 显示 OpenClaw 有 3,461 个 open issue，Hermes 有 2,768 个 open issue，因此本文是主题情报切片，不是完整工单清单。

Signal strength was weighted by current openness, comment count, reaction count, priority labels where present, and repeated patterns across nearby issues. I avoided long quotations from issue bodies and cite source issues directly for follow-up.

信号强度按当前未关闭状态、评论数、reaction 数、已有优先级标签，以及相邻 issue 中的重复模式加权判断。本文不长篇引用 issue 正文，只直接链接来源 issue 供后续追踪。

## 总体结论 / Overall Takeaway

OpenClaw currently looks like a fast-moving agent runtime (the process layer that starts agents, schedules work, calls tools, and routes messages) whose sharpest unresolved pain is operational reliability: gateway (the long-running bridge between CLI/platform channels and agent execution) CPU saturation, startup stalls, TUI (terminal user interface, the command-line visual UI) connection hangs, packaged channel dependency regressions, and cross-channel delivery leaks repeat across recent releases. Its older high-comment issues show durable product demand around desktop/mobile companions, richer messaging surfaces, skill ecosystem quality, memory behavior, and secret isolation.

OpenClaw 当前像一个高速迭代的 agent runtime（智能体运行时，负责启动、调度、工具调用和消息通道），最尖锐的未解决痛点是运行可靠性：gateway（网关，连接 CLI、平台通道与 agent 执行的常驻进程）CPU 饱和、启动卡顿、TUI 连接挂起、打包通道依赖回归、跨通道输出泄露，在近期版本中反复出现。较早的高评论 issue 则显示桌面/移动端 companion、富消息能力、skill 生态质量、memory 行为与密钥隔离仍是长期产品需求。

Hermes currently shows a broader spread: model/provider (the selected model plus the service adapter that sends requests to it) boundary correctness, gateway resource leaks, tool execution edge cases, session/memory continuity, Docker and setup friction, plus governance around self-improving skills (agent-authored skill changes that can alter future behavior). The strongest recent labels include `P1` gateway leaks and provider/tool failures, while the most-commented older issues point to auditability, memory architecture, multi-agent support, Matrix/Feishu platform maturity, and credential isolation.

Hermes 当前问题分布更广：模型/provider 边界正确性、gateway 资源泄漏、工具执行边界、session/memory 连续性、Docker 与安装体验摩擦，以及 self-improving skills（自我改进技能，即 agent 自动生成或修改自身能力说明）治理。近期最强标签包括 `P1` gateway 泄漏与 provider/tool 失败；较早高评论 issue 指向审计能力、memory 架构、多 agent 支持、Matrix/Feishu 平台成熟度与凭据隔离。

## 架构与运行时缺口 / Architecture and Runtime Gaps

OpenClaw's most urgent current runtime theme is gateway event-loop starvation and degraded startup. Recent open issues report 100% CPU, slow `node.list`, and memory pressure in [openclaw#75688](https://github.com/openclaw/openclaw/issues/75688), gateway CPU root causes in [openclaw#75707](https://github.com/openclaw/openclaw/issues/75707), Raspberry Pi and ARM64 WebSocket starvation in [openclaw#75703](https://github.com/openclaw/openclaw/issues/75703), Windows Telegram saturation across releases in [openclaw#75687](https://github.com/openclaw/openclaw/issues/75687), and per-turn startup overhead on WSL2 in [openclaw#75676](https://github.com/openclaw/openclaw/issues/75676). WebSocket (a persistent bidirectional network connection used by browser/CLI clients) stalls also explain why TUI and cron symptoms cluster with gateway health.

OpenClaw 当前最紧急的运行时主题是 gateway event-loop starvation（事件循环饥饿，单线程异步调度被长任务堵住）与启动退化。近期 open issue 报告 [openclaw#75688](https://github.com/openclaw/openclaw/issues/75688) 中的 100% CPU、缓慢 `node.list` 与内存压力，[openclaw#75707](https://github.com/openclaw/openclaw/issues/75707) 中的 gateway CPU 根因，[openclaw#75703](https://github.com/openclaw/openclaw/issues/75703) 中 Raspberry Pi 与 ARM64 WebSocket 饥饿，[openclaw#75687](https://github.com/openclaw/openclaw/issues/75687) 中 Windows Telegram 跨版本饱和，以及 [openclaw#75676](https://github.com/openclaw/openclaw/issues/75676) 中 WSL2 每轮启动开销。WebSocket（浏览器/CLI 客户端使用的持久双向网络连接）卡顿也解释了 TUI 和 cron 症状为何与 gateway 健康聚集在一起。

OpenClaw's packaging and plugin runtime also show repeated regressions. Recent examples include missing Discord/Telegram bundled channel runtime dependencies in [openclaw#75685](https://github.com/openclaw/openclaw/issues/75685), Telegram loader warnings in [openclaw#75733](https://github.com/openclaw/openclaw/issues/75733), Google secrets reloader crash loops in [openclaw#75797](https://github.com/openclaw/openclaw/issues/75797), external `web_fetch` provider lookup being limited to bundled plugins in [openclaw#74915](https://github.com/openclaw/openclaw/issues/74915), and Docker skill install failure because a Linux container expects Homebrew in [openclaw#14593](https://github.com/openclaw/openclaw/issues/14593). The repeated shape is that plugin contracts exist, but install/update/runtime resolution paths diverge.

OpenClaw 的打包与 plugin runtime 也反复回归。近期例子包括 [openclaw#75685](https://github.com/openclaw/openclaw/issues/75685) 中 Discord/Telegram bundled channel runtime dependency 缺失，[openclaw#75733](https://github.com/openclaw/openclaw/issues/75733) 中 Telegram loader warning，[openclaw#75797](https://github.com/openclaw/openclaw/issues/75797) 中 Google secrets reloader crash loop，[openclaw#74915](https://github.com/openclaw/openclaw/issues/74915) 中 external `web_fetch` provider lookup 被限制在 bundled plugin，以及 [openclaw#14593](https://github.com/openclaw/openclaw/issues/14593) 中 Docker skill install 因 Linux 容器预期 Homebrew 而失败。重复形态是 plugin contract（插件契约，声明插件能力与宿主如何调用）存在，但安装、升级与运行时解析路径发生分歧。

[openclaw#75799](https://github.com/openclaw/openclaw/issues/75799) reports OpenAI-compatible provider requests dropping prior session history, [openclaw#75720](https://github.com/openclaw/openclaw/issues/75720) reports plugin presets overwriting user-set primary models, [openclaw#74910](https://github.com/openclaw/openclaw/issues/74910) reports doctor migration discarding a legacy timeout value, and [openclaw#73306](https://github.com/openclaw/openclaw/issues/73306) keeps Active Memory timeout failures visible. Hermes 的 provider/tool 边界正确性是另一类重复运行时 cluster。[hermes#18478](https://github.com/NousResearch/hermes-agent/issues/18478) 是面向严格 provider 的 `P1` duplicate tool name 失败，[hermes#18470](https://github.com/NousResearch/hermes-agent/issues/18470) 报告 custom OpenAI-compatible provider 丢失请求字段，[hermes#18452](https://github.com/NousResearch/hermes-agent/issues/18452) 报告 ACP adapter（Agent Client Protocol 适配器，用于编辑器等客户端接入 agent）没有传递 fallback provider，[hermes#15551](https://github.com/NousResearch/hermes-agent/issues/15551) 报告 custom endpoint 只像普通聊天而不执行工具，[hermes#8270](https://github.com/NousResearch/hermes-agent/issues/8270) 报告 OpenRouter 在 curl 成功时仍失败。主题是 adapter parity（适配器一致性）：每个入口都必须保留相同的 provider、tool、fallback 与 transport contract。

## 安全缺口 / Safety Gaps

OpenClaw's safety signals concentrate on secrets, prompt injection, and output isolation. [openclaw#11829](https://github.com/openclaw/openclaw/issues/11829) is a security roadmap for protecting API keys from agent access, [openclaw#10659](https://github.com/openclaw/openclaw/issues/10659) asks for masked secrets that agents can use but not read, and [openclaw#45740](https://github.com/openclaw/openclaw/issues/45740) reports raw GitHub issue bodies being injected into sub-agent prompts. Prompt injection means untrusted text tries to steer the model or tools; the repeated signal is that external content and credentials still need stronger isolation boundaries.

OpenClaw 的安全信号集中在 secrets、prompt injection 与输出隔离。[openclaw#11829](https://github.com/openclaw/openclaw/issues/11829) 是保护 API key 不被 agent 访问的安全路线图，[openclaw#10659](https://github.com/openclaw/openclaw/issues/10659) 要求 masked secrets（可被 agent 使用但不可直接读取的密钥），[openclaw#45740](https://github.com/openclaw/openclaw/issues/45740) 报告原始 GitHub issue body 被直接注入 sub-agent prompt。Prompt injection（提示注入，非可信文本试图操纵模型或工具）意味着外部内容与凭据仍需要更强隔离边界。

OpenClaw also has user-visible leakage issues that are safety-adjacent. [openclaw#25592](https://github.com/openclaw/openclaw/issues/25592) reports text between tool calls leaking to messaging channels, [openclaw#65867](https://github.com/openclaw/openclaw/issues/65867) reports Gemini final tags leaking into delivered messages, and [openclaw#75726](https://github.com/openclaw/openclaw/issues/75726) reports internal runtime context wrappers leaking to Discord/Slack when echoed. These are safety gaps because internal scaffolding can reveal implementation state, confuse users, or expose sensitive context.

OpenClaw 也有与安全相邻的用户可见泄露问题。[openclaw#25592](https://github.com/openclaw/openclaw/issues/25592) 报告 tool call 之间的文本泄露到消息通道，[openclaw#65867](https://github.com/openclaw/openclaw/issues/65867) 报告 Gemini final tag 泄露到投递消息，[openclaw#75726](https://github.com/openclaw/openclaw/issues/75726) 报告 internal runtime context wrapper 在模型复述时泄露到 Discord/Slack。这些属于安全缺口，因为内部脚手架可能暴露实现状态、误导用户，或泄露敏感上下文。

Hermes safety demand is strongly tied to auditability and credential isolation. [hermes#487](https://github.com/NousResearch/hermes-agent/issues/487) has 21 comments for a cryptographic audit trail, meaning a tamper-evident action log linked by hashes; [hermes#4656](https://github.com/NousResearch/hermes-agent/issues/4656) proposes a zero-knowledge credential proxy daemon; [hermes#10575](https://github.com/NousResearch/hermes-agent/issues/10575) reports Claude OAuth/proxy usage being misclassified under a full prompt; and [hermes#11692](https://github.com/NousResearch/hermes-agent/issues/11692) asks for receipts proving which skill version produced which output.

Hermes 的安全需求强烈关联审计与凭据隔离。[hermes#487](https://github.com/NousResearch/hermes-agent/issues/487) 围绕 cryptographic audit trail（密码学审计链，用哈希串联动作日志以防篡改）有 21 条评论；[hermes#4656](https://github.com/NousResearch/hermes-agent/issues/4656) 提出 zero-knowledge credential proxy daemon（零知识凭据代理，让 agent 能调用凭据但不能看见凭据）；[hermes#10575](https://github.com/NousResearch/hermes-agent/issues/10575) 报告 Claude OAuth/proxy 在完整 prompt 下被误判；[hermes#11692](https://github.com/NousResearch/hermes-agent/issues/11692) 要求证明哪个 skill version 产生了哪个输出的 receipt（凭据/收据）。

Hermes self-improvement safety is an active governance gap. [hermes#17583](https://github.com/NousResearch/hermes-agent/issues/17583) asks for user-locked versus self-improving skill tiers and user-feedback-driven updates. This matters for Quilin because any self-evolving framework needs explicit provenance, approval, and rollback boundaries before agent-authored skills can modify durable behavior.

Hermes 的自我改进安全是活跃治理缺口。[hermes#17583](https://github.com/NousResearch/hermes-agent/issues/17583) 要求区分 user-locked skill tier 与 self-improving skill tier，并让 skill 更新由用户反馈驱动。这对 Quilin 很重要，因为任何自进化框架在允许 agent-authored skill 修改持久行为前，都需要明确的来源、审批与回滚边界。

## 文档与开发者体验缺口 / Documentation and Developer-Experience Gaps

OpenClaw's developer-experience pain often appears where documented or implied contracts do not match actual runtime behavior. [openclaw#75764](https://github.com/openclaw/openclaw/issues/75764) reports a documented subagent thinking config path blocked by `config.patch`, [openclaw#29387](https://github.com/openclaw/openclaw/issues/29387) reports `agentDir` bootstrap files silently ignored, [openclaw#22438](https://github.com/openclaw/openclaw/issues/22438) asks for tiered bootstrap loading to control token cost, and [openclaw#50090](https://github.com/openclaw/openclaw/issues/50090) frames community skill development and ClawHub as a gap between promise and practice.

OpenClaw 的开发者体验痛点经常出现在文档或隐含契约与实际运行行为不一致的地方。[openclaw#75764](https://github.com/openclaw/openclaw/issues/75764) 报告文档里的 subagent thinking config path 被 `config.patch` 拦截，[openclaw#29387](https://github.com/openclaw/openclaw/issues/29387) 报告 `agentDir` bootstrap file 被静默忽略，[openclaw#22438](https://github.com/openclaw/openclaw/issues/22438) 要求分层 bootstrap loading 控制 token 成本，[openclaw#50090](https://github.com/openclaw/openclaw/issues/50090) 将社区 skill 开发与 ClawHub 描述为承诺与实践之间的落差。

OpenClaw also has automation and operator DX gaps. [openclaw#75793](https://github.com/openclaw/openclaw/issues/75793) reports model auth login requiring an interactive TTY, which blocks Ansible/scripts/remote provisioning; [openclaw#75794](https://github.com/openclaw/openclaw/issues/75794) reports cron subcommands depending on gateway RPC (remote procedure call, a request from one process to another) when the gateway is degraded; and [openclaw#32473](https://github.com/openclaw/openclaw/issues/32473) reports confusing device-identity requirements for the control UI. The theme is that headless and production operators need explicit non-interactive paths and clearer diagnostics.

OpenClaw 也有自动化与 operator DX 缺口。[openclaw#75793](https://github.com/openclaw/openclaw/issues/75793) 报告 model auth login 要求 interactive TTY（交互式终端），阻塞 Ansible、脚本和远程 provisioning；[openclaw#75794](https://github.com/openclaw/openclaw/issues/75794) 报告 cron subcommand 在 gateway 退化时仍依赖 gateway RPC（远程过程调用，一个进程向另一个进程发请求）；[openclaw#32473](https://github.com/openclaw/openclaw/issues/32473) 报告 control UI 的 device identity 要求令人困惑。主题是无头运行与生产 operator 需要明确的非交互路径和更清晰诊断。

Hermes setup and deployment DX has repeated friction. Recent examples include Docker home-directory permission failure in [hermes#18482](https://github.com/NousResearch/hermes-agent/issues/18482), non-interactive setup prompt failures in [hermes#17579](https://github.com/NousResearch/hermes-agent/issues/17579), Python version installation errors in [hermes#17597](https://github.com/NousResearch/hermes-agent/issues/17597), stale `uv.lock` metadata in [hermes#17556](https://github.com/NousResearch/hermes-agent/issues/17556), and prompt-toolkit setup crash in [hermes#5884](https://github.com/NousResearch/hermes-agent/issues/5884). These are not just docs bugs; they decide whether new users can complete a first run.

Hermes 的安装与部署 DX 有重复摩擦。近期例子包括 [hermes#18482](https://github.com/NousResearch/hermes-agent/issues/18482) 中 Docker home-directory 权限失败，[hermes#17579](https://github.com/NousResearch/hermes-agent/issues/17579) 中非交互 setup prompt 失败，[hermes#17597](https://github.com/NousResearch/hermes-agent/issues/17597) 中 Python 版本安装错误，[hermes#17556](https://github.com/NousResearch/hermes-agent/issues/17556) 中 stale `uv.lock` metadata，以及 [hermes#5884](https://github.com/NousResearch/hermes-agent/issues/5884) 中 prompt-toolkit setup crash。这些不只是文档 bug；它们决定新用户能否完成首次运行。

Hermes TUI and dashboard DX has visible correctness gaps. [hermes#18511](https://github.com/NousResearch/hermes-agent/issues/18511) reports analytics head-of-line blocking, [hermes#18465](https://github.com/NousResearch/hermes-agent/issues/18465) reports inconsistent TUI exit resume summaries, [hermes#18449](https://github.com/NousResearch/hermes-agent/issues/18449) reports resize corruption, [hermes#18448](https://github.com/NousResearch/hermes-agent/issues/18448) reports live streaming truncation without expansion, and [hermes#18441](https://github.com/NousResearch/hermes-agent/issues/18441) reports dashboard resume opening an empty session. These indicate that operator interfaces need the same contract discipline as backend APIs.

Hermes 的 TUI 与 dashboard DX 有可见正确性缺口。[hermes#18511](https://github.com/NousResearch/hermes-agent/issues/18511) 报告 analytics head-of-line blocking（队头阻塞，一个慢请求挡住其他请求），[hermes#18465](https://github.com/NousResearch/hermes-agent/issues/18465) 报告 TUI exit resume summary 不一致，[hermes#18449](https://github.com/NousResearch/hermes-agent/issues/18449) 报告 resize 后界面损坏，[hermes#18448](https://github.com/NousResearch/hermes-agent/issues/18448) 报告 live streaming 截断且不能展开，[hermes#18441](https://github.com/NousResearch/hermes-agent/issues/18441) 报告 dashboard resume 打开空 session。这说明 operator interface 需要与后端 API 一样严格的 contract discipline（契约纪律）。

## 对 Quilin Core Loop 的启发 / Implications for Quilin Core Loop

For Quilin, the OpenClaw signal argues for keeping the core loop small only if the surrounding runtime contracts are explicit: startup stages, provider request assembly, tool/result sanitization, channel delivery, and background task announcements all need traceable handoffs. The relevant warning signs are OpenClaw's history drop in [openclaw#75799](https://github.com/openclaw/openclaw/issues/75799), phantom webchat messages in [openclaw#75784](https://github.com/openclaw/openclaw/issues/75784), subagent completion announcement issues in [openclaw#75785](https://github.com/openclaw/openclaw/issues/75785) and [openclaw#75663](https://github.com/openclaw/openclaw/issues/75663), and user-facing internal-output leakage in [openclaw#25592](https://github.com/openclaw/openclaw/issues/25592).

对 Quilin 来说，OpenClaw 信号说明：只有外围运行时契约足够明确，core loop 保持小才是安全的。startup stage、provider request assembly、tool/result sanitization、channel delivery、background task announcement 都需要可追踪 handoff（交接点）。相关预警包括 [openclaw#75799](https://github.com/openclaw/openclaw/issues/75799) 的历史丢失，[openclaw#75784](https://github.com/openclaw/openclaw/issues/75784) 的 phantom webchat message，[openclaw#75785](https://github.com/openclaw/openclaw/issues/75785) 与 [openclaw#75663](https://github.com/openclaw/openclaw/issues/75663) 的 subagent completion announcement 问题，以及 [openclaw#25592](https://github.com/openclaw/openclaw/issues/25592) 的内部输出泄露。

For Quilin, the Hermes signal argues that adapter parity and state migration should be first-class test axes. ACP, CLI, gateway, cron, TUI, and messaging surfaces must pass the same model/provider/fallback/tool contract, and session compression or reset must migrate goals, memory pointers, and delivery bindings. The clearest Hermes examples are [hermes#18478](https://github.com/NousResearch/hermes-agent/issues/18478), [hermes#18452](https://github.com/NousResearch/hermes-agent/issues/18452), [hermes#18467](https://github.com/NousResearch/hermes-agent/issues/18467), [hermes#18457](https://github.com/NousResearch/hermes-agent/issues/18457), and [hermes#18442](https://github.com/NousResearch/hermes-agent/issues/18442).

对 Quilin 来说，Hermes 信号说明 adapter parity 与 state migration 应成为一等测试轴。ACP、CLI、gateway、cron、TUI 与消息平台入口必须传递同一套 model/provider/fallback/tool contract；session compression 或 reset 必须迁移 goal、memory pointer 与 delivery binding。最清晰的 Hermes 例子是 [hermes#18478](https://github.com/NousResearch/hermes-agent/issues/18478)、[hermes#18452](https://github.com/NousResearch/hermes-agent/issues/18452)、[hermes#18467](https://github.com/NousResearch/hermes-agent/issues/18467)、[hermes#18457](https://github.com/NousResearch/hermes-agent/issues/18457) 与 [hermes#18442](https://github.com/NousResearch/hermes-agent/issues/18442)。

The safety lesson for Quilin is that self-evolution should not begin as free mutation. It should begin as provenance-aware proposals with explicit user lock zones, masked secrets, source isolation for untrusted issue bodies, and auditable action logs. The strongest external anchors are OpenClaw's [openclaw#11829](https://github.com/openclaw/openclaw/issues/11829), [openclaw#10659](https://github.com/openclaw/openclaw/issues/10659), [openclaw#45740](https://github.com/openclaw/openclaw/issues/45740), plus Hermes' [hermes#487](https://github.com/NousResearch/hermes-agent/issues/487), [hermes#4656](https://github.com/NousResearch/hermes-agent/issues/4656), [hermes#11692](https://github.com/NousResearch/hermes-agent/issues/11692), and [hermes#17583](https://github.com/NousResearch/hermes-agent/issues/17583).

对 Quilin 的安全启发是：self-evolution 不应从自由 mutation（自动修改持久代码或技能）开始，而应从 provenance-aware proposal（带来源记录的提案）开始，并有明确用户锁定区、masked secrets、非可信 issue body 来源隔离与可审计 action log。最强外部锚点是 OpenClaw 的 [openclaw#11829](https://github.com/openclaw/openclaw/issues/11829)、[openclaw#10659](https://github.com/openclaw/openclaw/issues/10659)、[openclaw#45740](https://github.com/openclaw/openclaw/issues/45740)，以及 Hermes 的 [hermes#487](https://github.com/NousResearch/hermes-agent/issues/487)、[hermes#4656](https://github.com/NousResearch/hermes-agent/issues/4656)、[hermes#11692](https://github.com/NousResearch/hermes-agent/issues/11692)、[hermes#17583](https://github.com/NousResearch/hermes-agent/issues/17583)。
