## MEDIUM

### MEDIUM-1. Loader path is not backward-compatible with old cache manifests missing `requested_max_rows`

Evidence:

- `benchmarks/src/datasets/cache.ts:16-27` requires `requested_max_rows` in `datasetManifestSchema`.
- `benchmarks/scripts/fetch-benchmark.ts:98-104` writes the new field, and `benchmarks/scripts/fetch-benchmark.ts:230-246` uses it correctly for fetch-skip intent.
- Probe with an otherwise valid pre-R1 manifest missing only `requested_max_rows` failed in `loadSweBenchVerifiedTasks()` with `CacheError ... (requested_max_rows)`.

Impact:

Fresh fetches are correct, and partial cache cannot masquerade as full cache anymore. The compatibility gap is specifically for users or CI jobs that already have an old `.benchmarks/datasets/*/manifest.json` and call the loader directly without re-running the fetch CLI. That path now hard-fails instead of treating missing `requested_max_rows` as legacy `null` or forcing a clear refetch flow.

Required fix:

Either document this as an intentional cache schema break, or add a migration-compatible parse path that treats missing `requested_max_rows` as legacy full only when `rows === expectedRowsFor(dataset)` and rejects legacy partial-as-full.

## Extra Boundary Probes

- `--memory-swap=N --memory=N`: implementation passes equal values; Docker CLI help confirms `--memory-swap` is the swap limit flag. This is enough for the intended no-extra-swap configuration at the CLI-args level.
- `docker rm -f` without `-v`: current implementation uses only bind mounts (`benchmarks/src/sandbox/docker.ts:324-332`). Docker `rm -v` targets anonymous volumes, so not using `-v` does not create a dangling-volume finding for this MVP.

No active unknown-leaderboard fixture was found.
