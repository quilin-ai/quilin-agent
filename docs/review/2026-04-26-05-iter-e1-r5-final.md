## Findings

### BLOCKING

#### BLOCKING-1. `file://` command token 可绕过 workspace path containment

证据：

- `assertCommandTokenContained()` 在 token 命中 `isUrlToken()` 时直接 return（`benchmarks/src/runner/runner.ts:472-479`）。
- `isUrlToken()` 使用的 scheme 白名单包含 `file://`（`benchmarks/src/runner/runner.ts:599-600`；pattern 定义见 `:145`）。
- 本地 fake `shell_exec` probe 未执行真实命令，只观察 runner 是否会把命令交给工具：
  - `cat /tmp/example`：blocked，fake tool 未调用。
  - `curl file:///tmp/example`：allowed，fake tool 被调用。
  - `cat file://tmp/example`：allowed，fake tool 被调用。

影响：

绝对路径 token 会被拦截，但同一类本地文件访问可通过 `file://` 形式进入工具层。真实 CLI 如 `curl file:///tmp/...`、`git clone file:///tmp/repo` 不需要 shell 展开即可读取本机路径；这绕过了 R2/R3/R4 修复想建立的 per-task workspace-only 边界。

建议：

不要把 `file://` 当作普通远端 URL 放行。至少对 `file://` token 转成本地路径后走 `assertPathContained()`；如果 benchmark runner 不需要本地 file URL，直接从 `urlSchemePattern` 移除 `file` 更简单。补测试覆盖 `file:///tmp/example` 拒绝、`https://x.com/y` / `ssh://...` 继续允许。

## Decision

**Iter E1 收口：no**。

理由：R5 对指定输入类别的本地 probe 证明 R4 修复覆盖了 option assignment 与 symlink/path 基础边界，cache resolver 也符合测试意图；但 `file://` 本地文件 URL 仍能穿过 command-token sandbox。这是 workspace containment 的直接绕过，应先修复并补测试后再收口。

## Codex Mainline Reconciliation

主线复核同意 R5 结论：**Iter E1 不收口**。此外，主线 probe 复现了两个 R5 报告未覆盖的 token parser 缺口；这两个缺口同样落在 ADR-010 §3.7 的 `shell command 中的路径 token 必须落在 workspace 内` 边界。

### Additional BLOCKING

#### BLOCKING-2. command redirection-like token 中的 path 未进入 containment

证据：`runBenchmarkTask()` + fake `shell_exec` probe（fake tool 只记录调用，不执行真实命令）：

| 输入 | Observed outcome |
|---|---|
| `echo ok >/tmp/r5-out` | allowed；fake tool called |
| `echo ok 2>/tmp/r5-err` | allowed；fake tool called |
| `cat </tmp/r5-in` | allowed；fake tool called |
| `echo ok >../r5-out` | allowed；fake tool called |

原因：`benchmarks/src/runner/runner.ts` 的 `commandTokens()` 只按 quote / whitespace 切 token，不像实际 `shell_exec` parser 一样拆 `<` / `>` / `2>` 操作符；因此 `>/tmp/x` 和 `>../x` 这类含路径的 token 没有被当作 path value 处理。

备注：当前 agent-core 内置 `shell_exec` 使用 `execFile`，降低了 shell redirection 的直接副作用；但 benchmark runner 的注入工具契约不能假设所有 `shell_exec`-compatible tool 都采用同一 parser。按 ADR-010 §3.7，runner wrapper 应在交给工具前拒绝这些 path token。

#### BLOCKING-3. 多重 assignment 中的 nested path 可绕过 containment

证据：

| 输入 | Observed outcome |
|---|---|
| `tool --key=value=/tmp/example` | allowed；fake tool called |
| `tool --key=a=b=/tmp/example` | allowed；fake tool called |

原因：R4 fix 的 `assignmentTokenValue()` 按第一个 `=` 拆分，随后对整个 value 做一次 path-like 检查。`value=/tmp/example` 含 `/`，但被 `assertPathContained()` 当作 workspace-relative token 解析为 `<workspace>/value=/tmp/example`，没有识别出第二个 `=` 后的绝对路径。

建议：下一轮 fix 至少补：

- `file://` 不作为远端 URL 放行；要么拒绝，要么转成本地 path 后走 `assertPathContained()`
- `commandTokens()` 或后续 checker 覆盖 `<path`、`>path`、`2>path`、`>>path`、`2>>path`、`<path` 等 operator-attached path
- assignment value 若包含后续 `=`，继续检查每个 `=` 后的 segment，或显式拒绝包含 path separator 的 nested assignment
- 对上述输入补 fake-tool negative tests，验证 fake tool 未被调用
