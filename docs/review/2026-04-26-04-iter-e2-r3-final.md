## HIGH

### HIGH-1. Docker smoke 的新增隔离断言可以失败但仍报告通过

Evidence:

- `benchmarks/scripts/docker-smoke.ts:78-91` 调用 sandboxed `shell_exec`，但没有保存或检查 `execute()` 返回值。
- `benchmarks/scripts/docker-smoke.ts:85-88` 把 base/cache 只读、network deny、`wget` 存在性都编码在同一个 shell command 里；这些断言失败时会让 DockerSandbox command 返回 `isError: true` / non-zero exit。
- `benchmarks/scripts/docker-smoke.ts:94-97` scorer 只检查 agent 返回的 patch 是否为 string。
- `benchmarks/scripts/docker-smoke.ts:102-109` 后续只检查 artifact 和 phases；如果 artifact 已在断言失败前写出，smoke 仍可继续。
- 临时 probe 证明：即使 sandbox command 返回 `isError=true`、`exitCode=12`、`stderr=network-allowed`，只要 `runAgent` 忽略 tool result 并返回 patch，benchmark result 仍是 passed。

Impact:

Linux CI smoke 可能无法区分“只读 mount / network deny 断言真的通过”和“断言失败但 tool error 被 runAgent 忽略”。同样，`command -v wget` 在 busybox/scratch/定制 image 上失败时也只是 tool error；当前 smoke 没有把这种“probe 工具缺失”作为明确失败原因处理。这样会让 ADR-011 Day 0 Docker gate 出现 false positive，不能支撑 official / untrusted hard isolation 收口声明。

Required fix:

在 `docker-smoke.ts` 中保存 `const shellResult = await config.tools[0].execute(...)`，要求 `shellResult.isError === false`，解析 payload 并要求 `exitCode === 0`、`timedOut === false`、`output_truncated === false`。网络 probe 也应显式区分三类结果：probe 工具缺失、网络被拒、网络意外允许；工具缺失应 fail fast 或换用 smoke image 中保证存在的 probe。然后在 Linux smoke 中实际验证 base/cache 写失败、task/artifacts 写成功、network denied、timeout enforced。

## LOW

### LOW-1. 两个 coverage 入口不是 include/root 差异，而是相同 denominator 下的 hit 差异

Evidence:

- 两个命令都发现 14 test files、197 passed / 1 skipped，并且 total denominator 相同：statements `844`、branches `521`、functions `180`、lines `836`。
- `--filter ... --configLoader runner` 得到 covered statements/branches `830/498`；`cd benchmarks && pnpm exec vitest run --coverage` 得到 `827/496`。
- 差异集中在 `src/sandbox/docker.ts`，例如 stderr truncation / output cap 相关行覆盖不同。

Impact:

这不是 coverage include/root 口径不同；更像 async stdout/stderr stream 命中顺序或 CLI 子进程输出截断测试的轻微非确定性。当前两条命令均高于 95%，不影响 E2 gate，但后续如果 branch coverage 靠近 95% 边界，可能再次产生误判。

Required fix:

把 output cap 的 stdout/stderr 分支改成 runner-level deterministic unit test，或把易受 stream race 影响的 coverage 断言改为不依赖实际子进程 chunk 顺序。

### LOW-2. Direct loader 仍只是 cache reader，不是 full-dataset gate

Evidence:

- `benchmarks/src/datasets/cache.ts:16-23` 允许 legacy manifest 缺 `requested_max_rows`，`readManifest()` 在 `:157-160` 归一化为 `null`。

- fetch CLI 路径已正确处理 full intent：`cacheSatisfiesRequest()` 要求 full fetch 时 `cachedMaxRows === null` 且 `cachedRows === expectedRowsFor(dataset)`（`benchmarks/scripts/fetch-benchmark.ts:230-245`），我的 legacy partial probe 也确认 full fetch 会 refetch。

Impact:

R2 要求的 legacy compatibility 与 partial-vs-full fetch 区分没有互相破坏；但直接调用 loader 读取旧 partial cache 时，loader 本身不会知道调用方是否需要 full Verified。考虑到当前 loader 也支持 shard/filter/smoke，这不作为 HIGH；官方 full run 不能绕过 fetch/manifest intent gate。

Required fix:

如需 official full-run API，增加显式 `requireFullDataset` / `expectedRows` 选项，或在 runner 的 official path 上先执行 fetch intent validation。
