## 3. Findings

### BLOCKING-1: lockfile finally cleanup 引发 stale 路径 race，invariant 被破坏

**File**: `benchmarks/scripts/fetch-benchmark.ts:216-219`

**实证代码**:
```ts
try {
  await handle.writeFile(...);
  return await operation();
} finally {
  await handle.close();
  await rm(lockPath, { force: true });   // <-- 无条件 rm
}
```

**Scenario**（reproduce-step-by-step）:
- T=0: Process A 调 `withDatasetFetchLock` → `open(lockPath, "wx")` 创建 inode A1，handle 持有 fd。开始长 GAIA fetch（165 rows + attachments）。
- T=10min+ε: Process B 调用 `withDatasetFetchLock`，`open` 抛 EEXIST → `removeStaleFetchLock` 读 `mtime`（A 写入时 set 一次，从不刷新；现在 mtime 已 10min+），判断 stale → `rm(lockPath, { force: true })` 把 A1 的目录项 unlink（A 仍持 fd）。
- B 继续 `while` 循环，`open(lockPath, "wx")` 成功，创建 inode B1。**A 和 B 现在并发跑 fetchBenchmarkWithLock，并发写 `data.jsonl` / `manifest.json` / `attachments/`，cache corruption。**
- T=15min: A 完成，进 `finally`：`handle.close()` → `rm(lockPath, force: true)`。**A 这次 rm 的是 B1 的目录项**（A1 已被 B unlink），即使 B 还在跑。
- T=15min+ε: Process C 来，看不到 lockfile，`open(... wx)` 直接成功，创建 inode C1 → **C 与 B 并发跑**。锁失效，cascade。

**为什么是 BLOCKING-1**:

1. 这违反了 R2 fix 加 lockfile 的根本不变量（"同 dataset 并发 fetch 被 serialize"）。
2. `rm(lockPath, { force: true })` 不区分 "我创建的那个 inode" 还是 "另一个进程的 inode"——POSIX 文件系统语义里，名字和 inode 是分离的，A 进程的 fd 指向 inode A1，但路径 `.fetch.lock` 已被 B 重新创建为 B1，A 的 `rm` 命中的是 B1。
3. cache corruption 后果：`data.jsonl` 一半是 A 写的、一半是 B 写的（或 rename atomicity 之外的中间状态），sha256 校验可能不直接抓到（因为 manifest 也是 B 后写的）。最坏情况：B 的 manifest 描述 B 的 data.jsonl，但 attachments 被 A、B 交叉写入 staging 后 rename 互相覆盖（参考 line 346-365 的 `stagingDir` + `rename`）。
4. 现有测试 `fetch-benchmark.test.ts:277-293` 只覆盖单 process 内的 stale lock 清理，没覆盖跨进程的 fd-vs-name race。

**Confidence**: 0.85（实证可走通；但需要 ≥ 10min 的长 fetch + stale 阈值同时满足；real GAIA fetch 在慢网络是真实场景，CI matrix 并发是 R2 fix 自己声称要解决的场景）

**修复建议**:
- 用 `proper-lockfile`（npm，battle-tested）或 `fcntl.flock` advisory lock，把 lock 绑到 fd 而不是 path。或：
- finally 段先 `fstat(handle.fd)` 拿当前 inode 号，再 `lstat(lockPath)` 比对 inode；不一致就只关 handle 不 rm。或：
- 在 lockfile body 写一个 unique nonce，`finally` rm 前先 `read` 比对 nonce，不匹配就跳过 rm。
- 补 reproduce 测试：spawn 两个 child process 串行启动相隔 10min+1s，确认串行真生效。

### HIGH-1: ADR-010 §3.1 attachment 字段未冻结类型，仅冻结字段名

**File**: `docs/adr/adr-010-benchmark-harness-wire-schema.md:56`

**实证文本**:
```
file_attachments[] 元素冻结为 {container_path, file_name, file_path, sha256, size_bytes}；
禁止包含 host_path / file_host_path / relative_path 等 host filesystem 细节。
```

**问题**: ADR-010 是 wire 契约，新 dataset 实现者读 ADR 不读 `cache.ts`。当前文本只列字段名，未约束：

- `sha256` 必须是 lowercase hex 64 字符（cache.ts:31 zod 用 `^[a-f0-9]{64}$`，ADR 没说）
- `size_bytes` 必须是 non-negative integer（cache.ts:32 zod nonnegative，ADR 没说）
- `container_path` / `file_path` 必须是 posix 形式 `/workspace/cache/datasets/<dataset>/attachments/<file>`（gaia.ts:15 hardcode，ADR 只说"当前"）
- `file_name` 必须是 `^[A-Za-z0-9._-]+$` 且 ≤255 bytes（gaia.ts:18 + 263 hardcode，ADR 没说）

**为什么是 HIGH 不是 BLOCKING**:
- defense-in-depth 已存在（cache.ts zod + gaia.ts pattern），合法 GAIA attachment 不会因此通过非法值。
- 但下一个 dataset（BFCL-v4 / 未来 OSWorld 等）实现者只看 ADR，可能写出"size_bytes 可以是 string" / "sha256 大小写混合" / "file_path 接受 host 绝对路径" 的代码——defense-in-depth 在 cache.ts 是 GAIA-only，新 dataset 自己实现 loader 时不一定有同样的 zod。

**Confidence**: 0.80（基于 R1/R2 已 land 的 ADR 约束精度纪律——其他冻结字段如 BenchmarkRun 都列了类型）

**修复建议**:
- ADR-010:56 字段名后加 `: type` 注释，比如 `{container_path: posix string, file_name: ^[A-Za-z0-9._-]+$ (≤255 bytes), file_path: posix string, sha256: lowercase hex 64, size_bytes: non-negative integer}`。
- 或在 ADR 里反引用 `benchmarks/src/wire/task.ts` zod schema 作为 normative 约束。

### HIGH-2: lockfile stale 阈值无 PID liveness check，long fetch 触发误清

**File**: `benchmarks/scripts/fetch-benchmark.ts:40, 209-211, 223-237`

**实证代码**:
```ts
const FETCH_LOCK_STALE_MS = 10 * 60 * 1000;   // line 40

await handle.writeFile(`${JSON.stringify({
  created_at: new Date().toISOString(),
  pid: process.pid,                            // line 209-211: 写 pid
})}\n`, "utf8");

async function removeStaleFetchLock(lockPath: string): Promise<boolean> {
  try {
    const lockStat = await stat(lockPath);
    if (Date.now() - lockStat.mtimeMs <= FETCH_LOCK_STALE_MS) {
      return false;
    }
    await rm(lockPath, { force: true });       // line 229: 不读 pid 直接删
    return true;
  ...
}
```

**问题**:
- lockfile body 写了 `pid: process.pid`（line 211），但 `removeStaleFetchLock` 完全不读它（line 223-237 只看 mtime）。pid 写了等于没写。
- 10 分钟 stale 阈值对 GAIA 全量 fetch 不够安全：165 rows × pageSize=100 = 2 page → 2 row fetch 调用；attachment fetch 是逐个串行（line 351-363 `for ... await writeFile`），如果 attachment 大小是 MB 级、HF 连接限速、retry 100ms*attempt 累计——10 分钟很容易吃掉。一旦超 10 分钟，**正在跑的进程 A 的 lock 被 B 误判 stale 删除，A 和 B 并发跑**（即使没有 BLOCKING-1 的 finally race，stale 误清本身就是错）。
- mtime 在 lock 创建时被 `writeFile` 设一次（line 208），跑长任务时不刷新；如果文件系统的 atime/mtime 行为是 noatime mount，mtime 更不会动。

**Confidence**: 0.75（HF 慢网络 + GAIA 165 行 + 多 MB attachment 是真实场景；test 端没法 hit 10min 真延时所以单测覆盖不到）

**修复建议**:
- 读 lock body 的 pid，用 `process.kill(pid, 0)` 检查活性（macOS 和 Linux 都支持；Windows 不支持但本仓库是 darwin/linux 主战场）。pid 仍在 → 即使 mtime stale 也不删；pid 已死 → 才删。
- 或用 heartbeat：长 fetch 期间定期 `utimes(lockPath, ...)` 刷 mtime（10min/2 = 5min 周期）。
- 或把阈值调到 30 分钟（牺牲 stale 恢复速度换安全），并在 ADR-010 §3.4 文档化。
- 文档化 lockfile 在 NFS / tmpfs / Docker overlay 的支持声明（ADR-010 §3.4 目前完全没提 lockfile）。

### LOW-1: Unicode digit zero-codepoint list 是 Unicode 16.0 snapshot，未来 Unicode 更新时 drift

**File**: `benchmarks/src/scorers/gaia-exact-match.ts:162-171`

**实证代码**:
```ts
const unicodeDecimalZeroCodePoints = [
  0x0030, 0x0660, ..., 0x1fbf0,  // 70 个 codepoint
] as const;
```

**问题**: 列表是手工维护的 snapshot，Unicode 标准每年更新 1 次（一般加 1-3 个新的 decimal digit script）；TS regex `\p{Nd}` 跟 V8 内置 Unicode table 走，可能比手工列表更新。drift 时 fold 失败，`\p{Nd}` 接受字符但 fold 不处理 → `Number(...)` 收到原 unicode 字符 → NaN → return false（FN 风险）。

**Confidence**: 0.55（drift 速度慢、score impact 小、且只影响极偏门的脚本）

**修复建议**: 注释说明 snapshot 来源和更新策略；或换成动态查 `unicodedata` 等价（Node 没有 stdlib，需要包）。可作为下一 iter chore。

## 4. R3 conclusion

**结论**: **fix-pass-needed**——R3 发现 BLOCKING-1（lockfile finally rm 在 stale-clean 与并发开锁之间制造 cascade race，破坏了 R2 fix 自己声称要建立的 serialize invariant），需要再修一轮。HIGH-1（ADR-010 字段类型未冻结）和 HIGH-2（stale 阈值无 PID liveness）应在同一轮一起修；MEDIUM-1（lockfile 协议未文档化）和 LOW-1（Unicode snapshot drift）可与 BLOCKING/HIGH 一起修，也可顺延下一 iter。

R2 在 BLOCKING-1 / HIGH-1 / HIGH-2 / MEDIUM-1 这四件 R2-标号问题上的修复**本身正确**（scorer 哨兵碰撞、host_path 泄漏、并发竞争、Unicode parity 都被代码或测试 cover），但**lockfile 实现引入的二阶问题超过 R2 自己声称解决的"跨进程 race"——R2 把 cache.ts 层面的 race 推到了 fs lock 层面的 race**。BLOCKING-1 没修之前，R3 不能 close。建议下一轮（R4 Faraday 或同会话补丁）按 §3 修复建议落地。

R3 不重提 R1/R2 已闭合的 8 项 finding（4+4），不重提 R1/R2 已 defer 的 3 项（MEDIUM-2 / MEDIUM-3 / LOW-1-graph）。R3 新发现 5 项（1 BLOCKING + 2 HIGH + 1 MEDIUM + 1 LOW），全部聚焦 R2 fix 引入的二阶副作用与 ADR 字段冻结精度。
