## 1. E3c1b1 first-cut delta 摘要

E3c1b1 落地了一个 Python long-session worker（`bfcl-stateful-worker.py`，443 行）+ TS thin adapter（`bfcl-stateful-runtime.ts`，422 行）+ contract tests（498 行）。worker 实现：

- JSONL command envelope：stdin `init_task / call_tool / snapshot / close`，stdout `ready / result / snapshot / closed / error`，所有 message 带 `id` 关联请求/响应
- 8-class whitelist（`SUPPORTED_BACKEND_CLASSES`）+ 4-class explicit reject（`UNSUPPORTED_BACKEND_CLASSES` 含 `WebSearchAPI / MemoryAPI_kv / MemoryAPI_vector / MemoryAPI_rec_sum`，与 pinned `f7cf735` `executable_backend_config.py` 实证一致）
- forbidden methods：`{kill, exit, quit, remove, unlink, popen, Popen, run}`，**完全等于** pinned `multi_turn_utils.py` 的 hardcoded blocklist（实证一致）
- structured call dispatch：`getattr(instance, method)(**arguments)`，**没有 `eval` / `exec` / `compile`**（grep 证实，worker 内仅 `json.loads` 和 attribute 访问）
- `validate_identifier` 强制 `^[A-Za-z_][A-Za-z0-9_]*$` 并 reject 任何 `_`-开头标识符 → 防 dunder access（`__class__` / `__getattribute__` 等）

TS adapter：spawn / per-call timeout（10s）/ idle timeout（60s）/ output bound（1MB）/ SIGINT-SIGTERM forward + cleanup deregister。

## 3. Findings

### BLOCKING

**BLOCKING-1：stderr 字节累积无上限（与 stdout 路径不对称）**
- 文件：`benchmarks/src/runtime/bfcl-stateful-runtime.ts:319-323`
- 现象：`handleStderr` 仅 per-chunk 比较 `chunk.byteLength > this.options.maxOutputBytes`，**不累积**。stdout 路径有 `this.stdoutBytes += chunk.byteLength` 累加（line 243-252），stderr 缺这一段。worker 不当输出（如 import 时 `mpmath` / `inspect` 在 Python 3.12+ 偶发 DeprecationWarning，几十 turn × 几 KB chunk）每条都 < 1MB → 永不触限，最终在 OS pipe buffer 内堆积可能反压 Python 写阻塞，或被丢弃淹没诊断信息。
- 实证对比：stdout 累积器存在（line 243）；stderr 同处不存在；测试 §`rejects malformed worker protocol output and bounded-output violations` 中 `largeStderrScript` 是单 chunk 64 字节 vs maxOutputBytes 8 → per-chunk 触发 SIGKILL，覆盖了"单 chunk 超限"分支，**未覆盖"累积超限"分支**。
- 修复方向：加 `stderrBytes` 字段，与 stdout 同款 `+= chunk.byteLength` 累加 + `> maxOutputBytes` 比对；同时加测试覆盖 N×小 chunk 累积超限场景。
- 严重度：BLOCKING — plan §6 风险段明确点名 "Python worker protocol deadlock" 包含 stderr backpressure；plan §5 验收 "AMB 100k p95 ≤ 300ms 不回归" 在 stderr 反压时无法保证；这是协议契约缺陷而非性能/风格。

**BLOCKING-2：error_type 表面"5 类"实际 10+ 类未对齐 plan**
- 文件：`benchmarks/src/runtime/bfcl-stateful-runtime.ts:148, 226, 246, 282, 345`
- 现象：plan §5 + sync-point S-e3c1b1-error-type 明确 "worker error_type 5 类（class_not_found / method_not_found / args_invalid / runtime_error / eval_security_violation）TS 端正确区分"；实测 TS adapter 在 worker 5 类之外**自创** 5 个：`worker_exit / worker_timeout / worker_output_limit / worker_protocol_error / worker_idle_timeout`。这些既不在 worker side（grep worker.py：5 个 ERROR_* 常量），也不在 plan 列举集；没有文档说明"TS 自创 vs worker 转发"区别；plan §6 点名的 `worker_oom / worker_stalled` 候选则未实现。
- 影响（具体可达 scenario）：E3c1b2 的 BFCL runner adapter 在 catch error 时无法可靠区分"worker 内执行错误"（应转结果失败给 LLM 看，让它自我纠正）vs "worker 进程错误"（应整个 task 中止 + 报警）。两层 error 都在同一 namespace（`tool_runtime_error` 来自 worker，`worker_timeout` 来自 TS adapter；都不带 layer 前缀）。E3c1b2 一旦写 `if (error.errorType === "tool_runtime_error") retry`，遇到 TS adapter 的 `worker_timeout` 会走 retry 分支但其实进程已死，无法 retry，task 卡住。
- 修复方向：
  1. 在 plan §5 + S-e3c1b1-error-type 显式补 5 个 TS-side error_type 命名空间（如前缀 `runtime.*` 而非 `worker_*`），或
  2. 把 5 个 TS error_type 改名加 `adapter_` / `runtime_` 前缀（与 worker error 严格区分）+ 加 docstring 注释
  3. 至少加 `BfclStatefulRuntimeError.layer: "worker" | "adapter"` 字段
- 严重度：BLOCKING — 协议契约不准确发往下游 E3c1b2；E3c1a R1 BLOCKING-1 catch-all 教训的核心就是"错误分类含糊导致下游静默坍缩"，此处复现该模式（不同 layer 同名空间）。

### HIGH

**HIGH-1：method 名冲突时 setdefault 静默选 first（无 ambiguous_method error_type）**
- 文件：`benchmarks/scripts/bfcl-stateful-worker.py:227`（`_refresh_method_mapping`）+ `:264`（`_resolve_method` no-prefix path）
- 现象：当 task `involved_classes` 含两个都有同名方法的 backend，`method_to_class` 用 `setdefault` 注册"第一次见就锁"。无前缀调用永远走第一个 backend，**不报错也不告警**。
- 实证：本 review 无 vendor 本地 BFCL upstream，无法直接 grep 真实 collision；但 worker 设计上**没有任何机制检测冲突**。即使当前无冲突，未来 BFCL 升级或 Quilin 自定义扩展会无声坍缩。注意：BFCL 官方 `_process_method_calls` 走的是 `instance_name` 前缀注入路径（不是裸动词），所以官方那条路径不会触发；worker 接受裸 method name 是 Quilin 自己的 quality-of-life 扩展，正好是 attack 面。
- 修复方向：`_refresh_method_mapping` 检测冲突时存"ambiguous"标记，无前缀调用 ambiguous method 时 throw `ERROR_TOOL_METHOD_NOT_FOUND`（或新增 `ERROR_AMBIGUOUS_METHOD`），强制要求带 class prefix。加测试：mock 两个 backend 都有 `ping`，无前缀调用 → reject。
- 严重度：HIGH — 直接破坏 plan §1 "preserves Python object identity and mutation across all steps and turns" 的语义保证（错的 instance 收到 mutation）。但严重度受限于"是否真有 collision"未实证，故 HIGH 而非 BLOCKING。

### MEDIUM

**MEDIUM-1：protocol_version 无 negotiation**
- 文件：worker.py:58, 285-289 + runtime.ts（无对应处理）
- 现象：worker 在初始 `ready` 写 `protocol_version: 1`；在 `init_task` 响应也写 `protocol_version: 1`。TS adapter `handleWorkerLine` 的 ready 分支（line 291）只 resolve startup ready，不读取 `protocol_version`。E3c1b2 升 v2 时 TS adapter 不会预警。
- 修复方向：TS adapter 在 startup ready 处比对 `message.protocol_version`，与 hardcoded `EXPECTED_PROTOCOL_VERSION = 1` 不同则 throw `protocol_version_mismatch`。
- 严重度：MEDIUM — 只是文档/forward-compat。

**MEDIUM-2：close() 极窄窗口缺 SIGKILL fallback**
- 文件：`benchmarks/src/runtime/bfcl-stateful-runtime.ts:199-210`
- 现象：close 走 `await sendCommand({type: "close"})` → finally 内仅 `child.kill("SIGTERM")`。**主 hang 路径有兜底**：worker 不响应 close 则 sendCommand 内部 timer（line 222-232）10s 后 SIGKILL，已正确处理。**仅极窄窗口暴露**：worker 已经 write+flush `{type:"closed"}`、TS 收到并 resolve `pending.resolve(message)` → 此时 worker 进程仍在跑 Python `__del__` / `weakref` finalizer / `atexit` hook（mpmath / pythonpath 修改后并非完全 clean），随后 TS finally 仅发 SIGTERM。如 finalizer 卡死或忽略 SIGTERM，无 SIGKILL 兜底。
- 修复方向：close 内加二段式：`SIGTERM` → 短 timeout（如 100-200ms）→ 若 `child.exitCode === null` 则 `SIGKILL`。
- 严重度：MEDIUM — 窗口窄；但若 host CI runner 累积，container/process 残留可能积累。

**MEDIUM-3：UTF-8 byte-safe forward-compat（latent，当前不可达）**
- 文件：`benchmarks/src/runtime/bfcl-stateful-runtime.ts:254`
- 现象：`handleStdout` 直接 `chunk.toString("utf8")`，对 multibyte 跨 chunk 边界会产生 U+FFFD。**当前不可达**：worker.py:419 `json.dumps(message, sort_keys=True, separators=(",", ":"))` 默认 `ensure_ascii=True`，stdout 全 ASCII，无 multibyte 序列。
- 风险触发条件：未来若 worker 改用 `ensure_ascii=False`（性能优化、节省字节、人类可读 trace 等）→ 立即 corruption。
- 对比：`benchmarks/src/scorers/bfcl-v4-multi-turn.ts:260-281` 已有 `appendBounded` + `decodeUtf8Prefix` byte-aware（E3c1a R1 落地）— 此处未复用，是 defense-in-depth 缺口。
- 修复方向：复用 `appendBounded` / `decodeUtf8Prefix` 同款，或维护 `Buffer` 累积 + 仅在每次 `\n` 处按 byte boundary slice + decode。亦可加 explicit assertion "worker stdout MUST be ASCII"（与 ensure_ascii 契约对齐）+ 检测违反时 fail-loud。
- 严重度：MEDIUM — 当前无 reachable exploit；plan §6 "沿用 E3c1a UTF-8 byte-safe 模式" 是 forward-compat 承诺，仅"未复用"是合理 advisory。

**MEDIUM-4：snapshot 每次 call_tool 都嵌入 → 7-turn × 多 backend 时 stdout 激增**
- 文件：worker.py:131-137（`call_tool` 返回 `state_snapshot`）+ runtime.ts:64（`defaultMaxOutputBytes = 1024*1024`）
- 现象：每次 `call_tool` 都附带完整 snapshot；多 backend（plan §5：8 class lifecycle 测试）+ `to_json_safe` 没有大小阈值（`MAX_SNAPSHOT_ITEMS=128` 是单层 cap，深度 `MAX_SNAPSHOT_DEPTH=6` 也是结构层级 cap，不是字节 cap）。极端任务 7 turn × 7 step/turn × 8 class snapshot × 几 KB 单 backend = 接近 1MB。
- 修复方向：`call_tool` 默认不返 snapshot；`snapshot` 单独命令调出来；或 snapshot 加 byte size cap + truncation 标记。
- 严重度：MEDIUM — E3c1b1 测试不会触；E3c1b2 真实 trajectory 才会现身。

### LOW

**LOW-1：start() 内 child.on("close") 顺序与 cleanup 重复**
- 文件：runtime.ts:149-159 + 175
- `child.on("close")` 内部已经 `cleanup()` + `rejectAll`；但 start() 失败路径 catch 里也调 `cleanup()` + `killChild("SIGKILL")`。两条路径都安全（idempotent），但代码可读性差（reviewer 难快速判断"哪条路径负责什么"）。
- 严重度：LOW — 仅风格。

**LOW-2：FORBIDDEN_METHOD_NAMES 与 BFCL 官方非 1:1 同步**
- worker.py:40-49 hardcoded `{kill, exit, quit, remove, unlink, popen, Popen, run}`；与 pinned `f7cf735` `multi_turn_utils.py` 行 92 完全相同。但若上游升级新增（如加 `eval_` / `compile_` 危险方法），worker 不会同步。
- 修复方向：load_executable_backend_config 同款，从 `multi_turn_utils.FORBIDDEN_METHODS`（如有）读，没有则告警。
- 严重度：LOW — 当前 pinned 一致；未来 spike 时再看。

## 4. R1 conclusion

**结果：fix-pass-needed**

- BLOCKING-1（stderr 累积无上限）：必修。stdout/stderr 路径不对称是协议契约缺陷，plan §6 "Python worker protocol deadlock" + §5 AMB p95 不回归承诺都受影响。
- BLOCKING-2（error_type 5 类名义实 10+ 类）：必修。两种解（plan 补充或 TS 改名）任选；不修会让 E3c1b2 在错误分类上重演 E3c1a R1 BLOCKING-1 catch-all 反模式。
- HIGH-1（method ambiguity）：应修，加防御 + 测试覆盖。
- MEDIUM × 4：建议修；MEDIUM-1（protocol_version）+ MEDIUM-3（byte-safe forward-compat）是低成本顺手活；MEDIUM-2（close 极窄窗口）+ MEDIUM-4（snapshot 激增）E3c1b2 时再看。
- LOW × 2：可选。

E3c1b1 进入 R1 fix（修 BLOCKING + HIGH），fix commit 后进入 R2 confirm。**不进入 close**。

E3c1b2 启动前提**不齐全**：worker contract 在 BLOCKING-2 修完前不稳定，`error_type` schema 还会变；E3c1b2 的 BFCL runner adapter 强依赖 worker 错误分类来决定"continue / abort task"语义。

### 下一步建议

1. fix 顺序：BLOCKING-1（stderr 累积，~5 行）→ BLOCKING-2（worker / TS error_type 命名空间对齐 + plan 同步更新，~10 行 + plan 1 段）→ HIGH-1（worker ambiguous_method，~10 行）
2. fix 验证硬指标：
   - 加 stderr accumulation test：N×小 chunk 总和超 cap → reject
   - 加 error_type discrimination test：worker 内 `tool_runtime_error` 与 TS adapter `runtime_*` 在 catch 端可区分（如 layer 字段或 prefix）
   - 加 ambiguity test：两 backend 同名 method 无前缀调用 → reject
3. MEDIUM-1（protocol_version negotiation）+ MEDIUM-3（UTF-8 forward-compat）顺手做也行
4. 修后 95% 覆盖率门 + just test-all 三语言绿 + AMB p95 ≤ 300ms 复测
5. R2 confirm（独立 subagent，仍不复用 11 名历史）
