## Findings

### HIGH

#### HIGH-1. Cache/runner filesystem containment 仍未处理 symlink/realpath escape

证据：

- Cache containment 只做字符串路径判断：`benchmarks/src/datasets/cache.ts:67-80` 用 `resolve(cacheDir, dataFile)` + `relative(cacheDir, dataPath)` + canonical filename regex。
- Cache 实际读取使用 `readFile(dataPath, "utf8")`：`benchmarks/src/datasets/cache.ts:115-117`。`readFile` 会跟随 symlink；当前代码没有 `lstat`/`realpath` 后确认目标仍在 cache dir 内。
- Runner containment 同样只做字符串路径判断：`benchmarks/src/runner/runner.ts:469-501` 用 `resolve(workspaceDir, value)` + `relative(root, candidate)`。
- `rg -n "realpath|lstat|readlink|stat\\(|symlink" benchmarks/src/datasets benchmarks/src/runner`：exit 1，无任何 realpath/lstat/symlink 覆盖。
- 现有测试只覆盖 lexical case：cache 覆盖 `../` / `/tmp` / `evil.jsonl`（`benchmarks/src/datasets/swe-bench-lite.test.ts:166-212`）；runner 覆盖 `~` / `/etc/hosts` / repo-root / `../secret.txt`（`benchmarks/src/runner/runner.test.ts:385-454`）。没有测试 `data.jsonl` 自身是 symlink、workspace 内 path/cwd 是 symlink、或 Windows drive-letter command token。

影响：

`data_file: "data.jsonl"` 仍是 canonical filename，但如果 `data.jsonl` 是指向 cache 外的 symlink，loader 会跟随读取；攻击者同时替换 manifest sha 时，当前校验不证明 bytes 来自 cache root 内。Runner 侧也无法证明传给工具的 `cwd/path` 最终 realpath 仍在 per-task workspace 内。R1 的 H2/B2 已关闭了明显的字符串替换和 cwd 默认注入，但没有关闭 symlink/realpath 攻击面。

建议：

Cache load：对 `cacheDir` 和 `dataPath` 做 `realpath`，并用 `lstat(dataPath).isSymbolicLink()` 或 realpath containment 拒绝 symlink escape；补 `data.jsonl -> outside` 且 sha 匹配的 negative test。Runner：对 path-like args 的 existing targets 做 realpath containment；对 cwd 必须 realpath；补 symlink cwd/path negative tests。Windows drive-letter 至少补 `C:\\...` token/field 单测，明确 POSIX-only 或跨平台策略。

### MEDIUM

#### MEDIUM-1. 强制 DI 后导出的默认 SWE scorer 是“可导入但不可用”的 DX 陷阱

证据：

- `benchmarks/src/scorers/swe-bench-patch-apply.ts:93` 仍导出 `sweBenchPatchApplyScorer = createSweBenchPatchApplyScorer()`。
- 但默认 executor 现在固定抛错：`benchmarks/src/scorers/swe-bench-patch-apply.ts:95-99`。
- `benchmarks/src/scorers/index.ts:16` 继续 re-export 这个 singleton。
- `benchmarks/src/scorers/registry.ts:11-47` 只提供 generic registry，没有提供带 `GitApplyCheckExecutor` 的 SWE scorer registration helper。
- `rg -n "runBenchmarkTask\\(|createSweBenchPatchApplyScorer\\(|sweBenchPatchApplyScorer|createShellExecGitApplyCheckExecutor|runAgent:" benchmarks packages docs/planning/2026-04-25-03-iter-e1-restart.md` 显示当前非测试调用基本不存在；也就是说当前不会破坏 CLI，因为还没有 runner CLI，但未来最容易注册的导出值默认会把有效 patch 计为 `executor_error`。

影响：

R1 H1 的安全问题通过“强制 executor DI”关闭是合理的；副作用是官方 scorer 的最显眼导出现在不可直接用于 registry/CLI。当前测试覆盖的是 fake executor 和 explicit failure，可能让真实 registration path 继续缺席。等 E2/E3 接官方 leaderboard CLI 时，这会变成样板/误用风险。

建议：

保留强制 DI，但移除或重命名默认 singleton，或提供 `createSweBenchScorerRegistry({ gitApplyExecutor })` / CLI composition helper，让正式入口必须显式传 executor，避免导入 `sweBenchPatchApplyScorer` 后静默全部失败。
