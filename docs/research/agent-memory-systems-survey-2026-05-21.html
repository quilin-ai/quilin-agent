一. 一句话总结 Executive Summary

目标不是再做一个记忆插件。目标是给麒麟做一个能打爆所有竞品的记忆系统:

  • 本地优先 — 数据全在你电脑上,不上云
  • 保留证据 — 每条提炼记忆都能追溯到原始对话片段
  • 时间正确 — 一年前住北京 vs 现在住深圳,两条都保留 + 标时间
  • 写入安全 — 任何修改都过写入审批门WriteAuthority,防误删 / 投毒
  • 长周期可测 — 写入完整性 + 检索准确率都能跑评测
  • 跨客户端共用 — 命令行 / 终端 / 网页 / Mac 应用全连同一份记忆

业界已经收敛出几个强组件 — Mem0 的快速抽取、Zep 的时间图谱、MemPalace 的原始证据保真、GBrain 的可靠后台任务、Claude Code 的文件记忆。但没有任何竞品同时具备:

  • 麒麟的全局写入审批门 — 统一管 14 类敏感操作
  • 麒麟的灵魂导入Soul Import — 一次扫描 6 个其他 agent(Claude Code/OpenClaw/Hermes/Codex/Gemini CLI/OpenCode)的本地配置文件,做冷启动
  • 麒麟的4 端共享 — 命令行 / 终端 / 网页 / Mac App 共享同一份本地数据库
  • 麒麟的技能系统(skill = 操作步骤记忆) + 自我进化闭环

核心策略:不为了层级而加层级。交付一个受治理的记忆操作系统。基础是"每条记忆都有出处 + 都能追溯历史版本 + 错了能回滚";检索时遇到不确定的情况主动拒答而不是瞎说;后台整理通过独立的后台服务quilin-daemon跑,不挤进对话路径。第一周不追逐所有 idea,先让记忆更安全、更可测。

二. 14 个竞品分成 5 类 Combined Overview

记忆库(给 Agent 当模块用)

mem0 · agentmemory · MemMachine 客户端

独立服务(自己起一个 server)

letta · zep · mempalace · MemMachine · gbrain

主机插件(挂在别的 agent 上)

hermes-agent · OpenClaw 记忆插件

Agent 自带原生记忆

codex · claude-code · OpenClaw

商用 / 领域专用

EverOS · TencentDB-Agent-Memory · claude-mem

最强模式是"共识",不是冲突。所有系统都需要:持久原始证据、抽取后的事实、融合检索、后台整理、用户画像存储。分歧在于"权力放在哪里":

派系代表权力归属
让大模型自己管Letta / AgeMem给 LLM 各种工具自己增删改
证据优先MemPalace / MemMachine先保留原始对话片段,再抽取
时间图谱真值Zep / Graphiti所有事实都带"什么时候是真的"
可靠后台任务GBrain / Codex把记忆整理放后台,带租约/心跳/重试
用户可见文件Claude Code / 各种 markdown记忆就是几个 .md 文件,你能直接看/改

麒麟应该组合这些共识部分,但权力必须放在大模型之外(走写入审批门,不能让 LLM 自己说"我决定记这个就记")。

已超前 业界没有的 3 项(打爆机会的基础)

1. 全局写入审批门WriteAuthority

竞品要么只在单个记忆模块内做门禁,要么完全没有。麒麟用一套审批门管 14 类敏感操作:文件写入、记忆增删改、技能创建、空闲时段写入、自演化提案。14 个竞品都没做到。

2. 4 客户端共享同一份本地记忆

命令行 / 终端 / 网页 / Mac 应用 共享 ~/.quilin/。比"只跑在服务器上"更难也更有价值。Mac App 上线前必须解决,只有麒麟面对、能解。

3. 灵魂导入Soul Import

第一次安装麒麟时,自动扫描 6 个其他 agent 的本地配置(Claude Code、OpenClaw、Hermes、Codex、Gemini CLI、OpenCode),把它们的用户偏好、习惯、项目笔记导入到麒麟的 user.md + soul.md + QUILIN.md。独特的冷启动优势 — 你不用从零教麒麟你是谁。

差距明显 10 项要补

  1. 缺生产级后台任务队列(带租约、心跳、过期任务抢占、运行上限)
  2. 缺完整版本链+ 快照 + 时光回溯接口
  3. 缺与每条派生事实相连的原始观察证据库
  4. 缺责任人范围的证据来源(多人、多客户端、导入的记忆都要标"谁写的")
  5. 缺多重验证检索和低置信度拒答(防大模型瞎说)
  6. 缺破坏性操作防护(删除前预览影响 + 软删除保留期 + 回滚)
  7. 缺与层级正交的记忆类型标签(用户偏好 / 反馈 / 项目笔记 / 引用 / 模式 / 工作流 / etc)
  8. 缺前瞻记忆(未来承诺 + 提醒)
  9. 缺对话轨迹自动编译成技能的成熟度流水线
  10. 缺多模态资源库或 schema 预留(截图 / PDF / 图片)

10 个升级方向详解

🔥 第 1 高:证据保存 + 版本链 + 时光回溯(原估 4-5 联合日 ≈ 实测 2-3 小时,QUI-193 ✅ ship)

给每条记忆加版本字段(版本号、父记录 ID、覆盖了谁、是不是最新、什么时候过期、可信度强度);加一张记忆来源表把每条派生事实指回一段或几段原始对话;加记忆快照表可以"回到上周三的记忆状态"。

核心规则:每次纠错都新建事件,不改写历史。比如"用户名是老孟" → "用户希望叫孟哥",老的记录标记"被覆盖",但不删除,留作历史。

Plane 实际工单:QUI-193 证据库 + 版本链 + 快照回溯(3 合 1 实施 · ✅ 已 ship,commit 414eb62)

🛡️ 第 2 高:安全检索门(原估 2-3 联合日 ≈ 实测 1-1.5 小时,QUI-194 ✅ ship)

在混合检索之上加一层"聪明的看门人"。规则:

  • 置信度低 → 返回"我不确定,你能再说一遍吗?"而不是瞎编
  • 检索到的 top 3 互相矛盾 → 跑多重验证(让大模型从多个角度评判)
  • 偏离结果 → 进隔离区,并生成"安全教训"记录,下次类似情况自动警觉

这是 A-MemGuard、MemX、OWASP Agent 防护、AgentPoison(投毒攻击防御)和麒麟已有 docs 的交汇点。

Plane 实际工单:QUI-194 安全检索门(低置信拒答 + 多重验证 2 合 1 实施 · ✅ 已 ship,commit ab1f758)

⚙️ 第 3 高:批量整理 + 破坏性操作防护(原估 3 联合日 ≈ 实测 1.5-2 小时,QUI-189 ✅ ship · QUI-195 ⏳ 第二周)

把"逐对判定"换成"批量集群判定" — 一次扔 10 对给大模型,返回结构化的"哪些是一组重复"。但用户界面不变(memory_consolidate_plan 接口不动)。

真正删除前必须:

  • 预览"如果删了这条,会影响哪些下游"
  • 走写入审批门让用户确认
  • 软删除保留 72 小时(可恢复)
  • 72 小时后才物理删

这把 QUI-189 批量判定升级成安全的生产整理路径,并吸收了 GBrain 的破坏防护设计。

Plane 实际工单:QUI-189 批量大模型判定(✅ 已 ship,commit 414eb62,9 条 → 1 call 205ms,20x 提速) · QUI-195 破坏防护(72h 软删 + 撤销 + 影响预览,⏳ 第二周)

📊 第 4 高:记忆完整性评测(原估 2 联合日 ≈ 实测 0.5-1 小时,QUI-192 ✅ ship)

本地搞一套自己的评测集,专门测"写入是否正确",而不只是测检索召回率。具体测:

  • 错误画像写入(把"用户是程序员"误写成"用户是医生")
  • "我参与的事" vs "我观察到的事"(权重不同)
  • 责任人归属(同一条记忆是 LLM 主动写的、还是 user 手动改的、还是从其他 agent 导入的)
  • 并发写入冲突
  • 覆盖更新
  • 回滚
  • 投毒
  • 无来源的"凭空生成"记忆
  • 中英文双语轮次

公开评测榜(LongMemEval / LoCoMo / BEAM)仍然跑,但 CI(自动测试管道)的守门员是本地的、可复现的。

Plane 实际工单:QUI-192 完整性评测(完整性 + 责任人归属 2 合 1 · ✅ 已 ship,commit ab1f758,9 核心 case + 35 测试)

⏰ 第 5 高:持久后台服务 quilin-daemon(原估 3-4 联合日 ≈ 预测 1.5-2.5 小时,QUI-188 ⏳ 第三周)

独立的后台进程(类似手机后台天气更新),跟主对话解耦。它管:

  • 每 24 小时跑一次整理
  • 反思器抽取知识
  • 自演化模块定期看有没有需要升级的脚手架
  • 用户行为模式挖掘
  • Token 预算监控
  • 未来可能的:技能自动安装、定期跑评测

设计要求:租约(同一任务不会两个进程同时跑)、心跳(死了能被发现)、过期任务抢占、重试退避、持久日志(重启后能接着跑)。

Plane 实际工单:QUI-188 quilin-daemon(后台服务框架 + 记忆任务队列 2 合 1 · ⏳ 第三周)

🔀 第 1 中:多客户端 + 项目范围(原估 3 联合日 ≈ 预测 1.5-2 小时,QUI-196 ⏳ 第二周)

给每条记忆加"最后是谁写的"标签(命令行 / 终端 / 网页 / Mac App)。当两个客户端同时改同一条记忆,要有冲突合并界面让用户决定。

把当前工作目录 + QUILIN.md 作为"检索时的加权信号" — 在 /repo/A 跟麒麟聊天,记忆优先返 A 项目的;切到 /repo/B,自动激活 B 项目的记忆。这是麒麟独有的机会,因为"只跑在服务器上"的系统不面对 4 客户端共享本地数据库的问题。

Plane 实际工单:QUI-196 多客户端 + 项目范围(多端冲突合并 + 项目检索加权 2 合 1 · ⏳ 第二周)

🛠️ 第 2 中:操作步骤记忆流水线(原估 4 联合日 ≈ 预测 2-3 小时,QUI-198 ⏳ 第四周)

用自演化对话轨迹 + 重复成功的任务模式,自动创建"案例记录"AgentCase。比如"用户连续 5 次让我跑 pytest + ruff + commit",系统识别出这是一个常用工作流。

当足够多类似高质量案例累积,后台服务自动生成一个 SKILL.md 候选,包含:

  • 什么场景该激活这个技能
  • 前置条件
  • 验证步骤
  • 预期证据
  • 失败 case
  • 出处(来自哪些对话)

但用户必须批准(走写入审批门)才能正式落地成技能。

Plane 实际工单:QUI-198 操作步骤流水线(AgentCase 案例 + 轨迹→技能提案 2 合 1 · ⏳ 第四周)

🔮 第 3 中:前瞻记忆 + 提前准备(原估 3 联合日 ≈ 预测 1.5-2 小时,QUI-199 ⏳ 第四周)

增加未来事项模型 — 用户的承诺、待办、提醒、有时间边界的意图。比如用户说"下周二我要见客户",麒麟记下来,周二之前自动提醒。

保守的提前准备:任务可预测且预算够时,后台服务预先准备可能需要的上下文。它不应该在用户提问前先回答,只是把证据 + 缓存备好,用户一问马上响应。

Plane 实际工单:QUI-199 前瞻 + 提前准备 + 证据可视化(3 合 1 · ⏳ 第四周)

🏷️ 第 4 中:重要性多维 + 类型标签 + 过期感知(原估 2 联合日 ≈ 预测 0.5-1 小时,QUI-197 ⏳ 第三周)

把单一的"重要性数字"替换成小向量:新颖性 / 实用性 / 个人相关度 / 可操作性 / 时效性 / 稳定性。按用户当前意图加权。

加与"层级"正交的类型标签:用户偏好 / 反馈 / 项目笔记 / 引用 / 模式 / Bug / 工作流 / 前瞻 / 资源。

Codex 找到的关键证据 / Key Evidence

1. MemoryLayer 是跨 3 处的硬枚举,不是单点

Python types.py:8、TS memory/types.ts:1、Web page.tsx:37 三处都固定 4 层(工作/情景/语义/技能)。加新层要改 3 处 + SQLite CHECK 约束 + 所有测试。

2. importance_score 不只在 SQLite

SQLite REAL + Python MemoryItem.coerce 强制 float + 归档策略数值比较 + TS 本地客户端直接当 number 用。替换成 JSON 会全链路破坏,只能 additive 加新字段。

3. memory_delete 当前是 Web 逐条调

Web /api/memory/route.ts:245 + dedupe 执行 /api/memory/dedupe/route.ts:215 都逐条调 MCP 工具。加破坏防护(72h 保留)会改 delete 语义 + Web 测试断言。

4. WriteAuthority 只在 TypeScript 侧

写入审批门当前是 packages/agent-core/src/safety/write-authority.ts 的 TS class。独立 Python daemon 无法直接复用,必须有 bridge 进程或跨语言协议。

5. SKILL.md 是 13-skills 文件系统唯一真源

docs/03-memory line 425/445 明文:技能路径归 13-skills 所有,03-memory 只镜像使用统计。操作步骤流水线必须通过 SKILL.md 提案路径,不能存 procedure body 到 memory。

核心架构规则

能用可选 metadata 或侧表承载能力时,不要新增 layer 或替换字段。Quilin 的优势是本地优先安全 + 写入审批门 + 多客户端上下文 + 灵魂导入可移植;保住这些边界,比照搬竞品分类体系更重要。

七. 双方共识 Consensus

Claude 跟 Codex 在以下原则上完全一致:

  • 麒麟应保持本地优先,而不是云端优先
  • 应先保留原始证据,再做语义抽取
  • 有后果的记忆修改必须走写入审批门
  • 评测分数是证据,不是产品目标(不刷榜)
  • 应实现持久后台调度,而不是各模块各自起循环
  • 操作步骤记忆应流经技能系统(13-skills),不重新发明
  • 项目 / 用户 / 灵魂这 3 个 markdown 文件应该是一等公民的记忆界面

"完美记忆"不是再加一个检索器,而是一个完整的、受治理的生命周期:

捕获 → 证明 → 检索 → 推理 → 整理 → 纠错 → 回滚 → 导出 → 评测

九. 它(Codex)独家视角 Codex-Unique View

Codex 看到我没特别强调的部分,主要是安全和评测形态:

  • 非大模型的原始证据(不让 LLM 是唯一写入方)
  • 写入完整性评测(测"写得对",不只是"找得到")
  • "我参与的事" vs "我观察到的事"(权重不同)
  • 责任人范围的证据来源
  • 低置信度检索拒答
  • 带验证的"对话轨迹→技能"编译

Codex 还明确反对"为了层级而加层级"的思路,认为 证据 / 时间 / 权威 / 评测 比层数多少更重要。

最高价值的独家洞察

"写入完整性" — 只测检索召回率不够。一个记忆系统可以通过召回测试,却静默污染用户身份、项目约束、流程规则。比如"用户偏好 Python"被错抹成"用户偏好 Java",检索召回测试看不出来。
