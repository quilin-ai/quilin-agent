# 执行隔离 / Execution Isolation

> SOTA survey, 2026-05-13. Bilingual format: English paragraph → 中文段落.

## 评估目标 / Goal

This document surveys the state of the art in three intertwined runtime concerns for a coding agent: (1) **OS-level sandboxing** of the shell-exec path so that a misclassified or jailbroken tool call cannot wipe the host, (2) **persistent shell sessions** so the model can run `cd`, set env vars, launch a long-lived server, and keep talking to it across turns, and (3) the **permission / approval model** that humans interact with when the agent wants to step outside its current ring. The goal is not to crown one winner but to pick, for each dimension, the single most credible path Quilin can take in 2026 with bounded engineering cost.

本文档调研编码 Agent 运行时三件互相耦合的事：(1) shell-exec 路径的**操作系统级沙箱**——一旦工具调用被误分类或被越狱，不能把宿主机抹掉；(2) **持久 shell 会话**——让模型可以 `cd`、设环境变量、起一个长期跑的服务，并在多轮对话里持续与它对话；(3) Agent 想跨当前权限环时人类介入的**权限 / 审批模型**。目标不是评出冠军，而是为每个维度挑出 2026 年 Quilin 在工程成本可控的前提下最可信的一条路。

## 业界 SOTA / Industry SOTA

### 1. 沙箱 / Sandbox

**sandbox-exec (Apple Seatbelt)** — Principle: kernel-level mandatory access control profile per process, written in TinyScheme-derived SBPL. License: macOS system binary. Last reality check: Apple has marked `sandbox-exec` "deprecated" since 2017 but still ships it in macOS 26.3 and uses it internally for BlastDoor; Chromium, Anthropic, and OpenAI continue to depend on it because there is no documented replacement at SBPL granularity (https://news.ycombinator.com/item?id=44283454, https://igorstechnoclub.com/sandbox-exec/). Strengths: zero-runtime-cost, MAC-grade isolation, used in production by Claude Code and Codex. Limits: undocumented profile language ("Apple System Private Interface"), no native FFI, deprecation-with-no-successor risk. Node TS integration: shell-out via `spawn("sandbox-exec", ["-p", profile, ...cmd])`. Adoption cost: 3-5 person-days to author and test 3-4 profiles (read-only / workspace-write / network / full). Risk: medium-low (works for everyone else; profile language drift across macOS versions is the main pain).

**sandbox-exec（Apple Seatbelt）**——原理：进程级内核 MAC 配置文件，用 TinyScheme 派生的 SBPL 写。许可：macOS 系统二进制。现实检查：Apple 自 2017 年起把 `sandbox-exec` 标为 "deprecated"，但 macOS 26.3 仍带它，并在 BlastDoor 等系统服务中自用；Chromium、Anthropic、OpenAI 持续依赖它，因为没有任何官方文档替代品能提供 SBPL 粒度（同上链接）。优点：零运行时成本、MAC 级隔离、Claude Code 与 Codex 都在生产使用。缺点：profile 语言无文档（"Apple System Private Interface"）、无原生 FFI、deprecate 但无继任者的风险。Node TS 集成路径：`spawn("sandbox-exec", ["-p", profile, ...cmd])`。采用成本：3-5 人日写并测试 3-4 个 profile（只读 / workspace-write / 联网 / 全开）。风险：中低（业界都在用；macOS 版本之间的 profile 漂移是主要痛点）。

**bubblewrap (bwrap) + Landlock + seccomp** — Principle: unprivileged Linux namespaces (user, PID, mount, network, IPC, UTS, cgroup) + read-only-by-default mount tree + optional Landlock filesystem rules + seccomp-bpf syscall filter. License: LGPL-2.0. Last release: bwrap 0.11.2 vendored by Codex v0.129 (May 2026) (https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md). Strengths: ~5 ms startup, no setuid root (unlike Firejail), Linux-only but standard, used by Flatpak, GNOME, and Codex; Landlock available since kernel 5.13 as a "self-restrict" capability that requires no daemon. Limits: needs `kernel.apparmor_restrict_unprivileged_userns=0` on Ubuntu 24.04+ (https://www.jdhodges.com/blog/codex-sandbox-ubuntu-24-04-fix/); does not work inside many Docker setups because the host strips the required user-namespace capabilities. Node TS integration: shell-out to `bwrap`, identical interface to `sandbox-exec`. Adoption cost: 4-7 person-days (parity with sandbox-exec plus a vendored fallback binary, which Codex bundles as `codex-resources/bwrap`). Risk: medium (Ubuntu AppArmor regression hit Codex hard in 2026 and required a vendored bwrap binary).

**bubblewrap (bwrap) + Landlock + seccomp**——原理：无特权 Linux 命名空间（user、PID、mount、network、IPC、UTS、cgroup）+ 默认只读的挂载树 + 可选 Landlock 文件系统规则 + seccomp-bpf 系统调用过滤器。许可：LGPL-2.0。最新发布：Codex v0.129（2026 年 5 月）vendored bwrap 0.11.2。优点：~5 ms 启动、不需要 setuid root（不像 Firejail）、Linux 限定但标准、被 Flatpak / GNOME / Codex 使用；Landlock 自内核 5.13 起作为"自约束"能力，无需 daemon。缺点：Ubuntu 24.04+ 需要 `kernel.apparmor_restrict_unprivileged_userns=0`；在许多 Docker 配置里不能用，因为宿主剥掉了 user-namespace 能力。Node TS 集成：shell-out 到 `bwrap`，接口与 `sandbox-exec` 等价。采用成本：4-7 人日（与 sandbox-exec 等价再加 vendored fallback；Codex 把 bwrap 二进制打进 `codex-resources/bwrap`）。风险：中（Ubuntu AppArmor 回归在 2026 年把 Codex 砸过一次，被迫 vendor bwrap）。

**gVisor (runsc)** — Principle: userspace application kernel in Go (the "Sentry") intercepts every guest syscall and re-implements ~360 of them, never letting the workload touch the host kernel; default platform is Systrap which uses seccomp-bpf for syscall trapping. License: Apache-2.0. 2026 status: rolling release, KVM and Systrap platforms, rootfs overlay default-on, used by Google Cloud Run and gVisor-on-GKE (https://gvisor.dev/docs/, https://github.com/google/gvisor). Strengths: VM-grade isolation without VM startup cost (~200 ms cold, sub-second warm), single attacker has to break the Sentry AND the host kernel to escape. Limits: ~10-30% syscall-heavy workload overhead, partial syscall coverage (some Linux APIs degrade or error), OCI-runtime — you need a container in the first place; not a drop-in for `spawn`. Node TS integration: only via OCI/Docker (`docker run --runtime=runsc`). Adoption cost: 8-12 person-days because you need to also ship a base image, a wiring layer, and a rootfs overlay. Risk: medium-high (heavyweight relative to bwrap; locks you into OCI tooling).

**gVisor (runsc)**——原理：Go 写的用户态应用内核（"Sentry"）拦截 guest 的每个系统调用并重新实现 ~360 个，永远不让 workload 摸到宿主内核；默认平台 Systrap 用 seccomp-bpf 做系统调用 trap。许可：Apache-2.0。2026 现状：滚动发布、KVM 与 Systrap 平台、rootfs overlay 默认开启、被 Google Cloud Run 与 gVisor-on-GKE 使用。优点：VM 级隔离，无 VM 启动开销（冷 ~200 ms，热亚秒），攻击者要同时打穿 Sentry 与宿主内核才能逃逸。缺点：系统调用密集 workload 有 ~10-30% 开销、部分系统调用降级或报错、本质是 OCI runtime——你得先有容器；不是 `spawn` 的 drop-in 替代。Node TS 集成：只能通过 OCI/Docker（`docker run --runtime=runsc`）。采用成本：8-12 人日，因为还要打基础镜像、写胶水层、配 rootfs overlay。风险：中高（相对 bwrap 重，绑定 OCI 工具链）。

**Firecracker** — Principle: KVM-based minimal VMM in Rust with only 5 emulated devices (virtio-net, virtio-block, virtio-vsock, serial, keyboard). License: Apache-2.0. Performance: ≤125 ms boot to `/sbin/init`, <5 MiB memory overhead per VM, 150 VMs/sec/host, sub-millisecond snapshot restore (https://github.com/firecracker-microvm/firecracker, https://firecracker-microvm.github.io/). Used by AWS Lambda, Fargate, Fly.io, Kata Containers. Strengths: real hardware virtualization boundary, the only option that survives a kernel-level guest exploit. Limits: Linux + KVM only (no macOS / Windows host); requires running as a VMM child process; you must build and ship a tiny guest rootfs and kernel; latency budget 125 ms is too slow for sub-second human interaction unless you snapshot-restore. Node TS integration: spawn `firecracker --api-sock` and talk JSON over Unix socket. Adoption cost: 15-20 person-days for a production pipeline. Risk: high (operational complexity; macOS dev loop excluded).

**Firecracker**——原理：Rust 写的极小化 KVM VMM，只模拟 5 个设备（virtio-net、virtio-block、virtio-vsock、串口、键盘）。许可：Apache-2.0。性能：启动到 `/sbin/init` ≤125 ms、每 VM 内存开销 <5 MiB、每宿主 150 VM/秒、亚毫秒 snapshot 恢复。用户：AWS Lambda、Fargate、Fly.io、Kata Containers。优点：真硬件虚拟化边界，是唯一在 guest 内核漏洞被打穿后仍能挡住的方案。缺点：Linux + KVM 限定（macOS / Windows 宿主不行）；必须以 VMM 子进程跑；要自己打 guest rootfs + 内核；125 ms 延迟对于亚秒级人机交互太慢，除非 snapshot 恢复。Node TS 集成：起 `firecracker --api-sock`，通过 Unix socket 发 JSON。采用成本：生产 pipeline 15-20 人日。风险：高（运维复杂度；macOS 开发循环不支持）。

**Apple Container (apple/container)** — Principle: per-container lightweight VM on macOS Virtualization framework, Swift-implemented, sub-second cold start. License: Apache-2.0. v0.9.0 released February 2026, ships with macOS 26 Tahoe (https://github.com/apple/container, https://opensource.apple.com/projects/container/). Strengths: official Apple, every container = its own micro-VM (a strictly stronger isolation than Docker Desktop which shares a single Linux VM), Docker-compatible CLI, no third-party deps. Limits: macOS 26+ only, pre-1.0, partial memory ballooning, no Linux/Windows. Node TS integration: shell-out to `container run`. Adoption cost: 3-5 person-days for a macOS-only opt-in path. Risk: low-medium for macOS users, irrelevant for the rest. **Best paired with bwrap-on-Linux as a platform-symmetric strategy.**

**Apple Container (apple/container)**——原理：基于 macOS Virtualization 框架的"每容器一台轻量 VM"，Swift 实现，亚秒冷启动。许可：Apache-2.0。v0.9.0 于 2026 年 2 月发布，随 macOS 26 Tahoe 出厂。优点：Apple 官方、每个 container = 独立 micro-VM（隔离强度严格高于 Docker Desktop 共享单一 Linux VM）、兼容 Docker CLI、无第三方依赖。缺点：仅 macOS 26+、pre-1.0、内存 ballooning 仅部分实现、无 Linux/Windows。Node TS 集成：shell-out 到 `container run`。采用成本：仅 macOS 路径 3-5 人日。风险：macOS 用户低中，非 macOS 用户无关。**最佳搭配：Linux 端用 bwrap，做平台对称策略。**

**Wasmtime + WASI Preview 2** — Principle: deny-by-default capability sandbox; the guest cannot open a file, socket, or env var unless explicitly granted via WIT-typed imports. License: Apache-2.0 (Bytecode Alliance). 2026 status: WASI 0.2 stable, 2-year LTS for production, Wasmtime is reference impl. Strengths: tightest theoretical sandbox, runs in-process, sub-millisecond instantiation, runtime-portable across Wasmtime / WasmEdge / WAMR / wazero. Limits: **the workload must be a Wasm module**, not an arbitrary shell command — `git`, `pnpm`, `python` cannot run; native binaries are out of scope until WASI Preview 3's process model lands. Recent CVE record (2026-04) shows it is an active target. Adoption cost: only relevant if Quilin were rewriting the toolchain itself to Wasm, which is out of scope; not viable for shell-exec sandboxing. Risk: not applicable for the shell path; potentially relevant for skill execution later.

**Wasmtime + WASI Preview 2**——原理：默认拒绝的能力沙箱；guest 不能打开文件、socket 或环境变量，除非通过 WIT 类型化的 import 显式授权。许可：Apache-2.0（Bytecode Alliance）。2026 现状：WASI 0.2 稳定、生产环境 2 年 LTS、Wasmtime 是参考实现。优点：理论上最紧的沙箱、进程内运行、亚毫秒实例化、跨 Wasmtime / WasmEdge / WAMR / wazero 可移植。缺点：**workload 必须是 Wasm 模块**，不是任意 shell 命令——`git`、`pnpm`、`python` 跑不了；原生二进制要等到 WASI Preview 3 的进程模型才能落地。2026-04 的 CVE 记录显示它是活跃攻击面。采用成本：仅当 Quilin 把工具链自己改写为 Wasm 时才相关，超出本次范围；对 shell-exec 不适用。风险：shell 路径不适用；将来可能与 skill 执行相关。

**nsjail** — Principle: namespaces + cgroups + seccomp-bpf via Kafel DSL. License: Apache-2.0 (Google). 2026 status: actively maintained, used by Google kCTF, Windmill, code-judge platforms (https://www.morphllm.com/nsjail-sandbox). Strengths: ~20 ms launch, very high throughput, fine-grained seccomp via Kafel. Limits: Linux only, mostly used for "execute one short submission then kill"; less ergonomic for long-running agent sessions than bwrap. Adoption cost: similar to bwrap (4-7 person-days). Risk: low-medium but bwrap has more daylight in agent tooling.

**nsjail**——原理：命名空间 + cgroups + 通过 Kafel DSL 的 seccomp-bpf。许可：Apache-2.0（Google）。2026 现状：活跃维护、Google kCTF 与 Windmill 与各种 code judge 平台在用。优点：~20 ms 启动、极高吞吐、Kafel 提供细粒度 seccomp。缺点：Linux 限定、主要面向"跑一个短任务然后杀掉"的场景；不像 bwrap 那样适合长 Agent 会话。采用成本：与 bwrap 持平（4-7 人日）。风险：低中，但 Agent 工具领域 bwrap 是主流。

### 2. 持久 Shell / Persistent Shell

**Claude Code BashTool background-task model** — `BashTool.tsx:14, 903-1000` shows that Claude Code does not maintain a single long-lived bash REPL; instead each call to `BashTool` is fresh, and only long-running commands get "backgrounded" into a `LocalShellTask` (`spawnShellTask`, `registerForeground`, `backgroundExistingForegroundTask`). Returned `shellId` lets the model poll or kill the task. State that survives across calls is just CWD (managed externally — `Shell.ts:447 setCwd`) and env. This is **simpler than a persistent PTY** but trades away true interactive REPL state (e.g., a Python repl).

**Claude Code BashTool 的后台任务模型**——`BashTool.tsx:14, 903-1000` 显示 Claude Code 不维护单一长生命周期 bash REPL；每次 BashTool 调用都是全新进程，只有长跑命令会被 backgrounded 成 `LocalShellTask`（`spawnShellTask`、`registerForeground`、`backgroundExistingForegroundTask`）。返回的 `shellId` 让模型可以 poll 或 kill。跨调用存活的状态只有 CWD（外部管理——`Shell.ts:447 setCwd`）和 env。这比真正的持久 PTY **简单**，代价是丢掉真正的交互式 REPL 状态（如 Python repl）。

**Codex `unified_exec` (PTY + process registry)** — `~/repo/codex/codex-rs/core/src/unified_exec/mod.rs:1-78` documents the model: each `unified_exec` call either creates a new PTY-backed process or reuses an existing process handle by id; output is buffered with head/tail caps (`UNIFIED_EXEC_OUTPUT_MAX_BYTES = 1 MiB`, `DEFAULT_MAX_OUTPUT_TOKENS = 10_000`); up to 64 concurrent processes per session (`MAX_UNIFIED_EXEC_PROCESSES = 64`, warning at 60). The handler split — `tools/handlers/unified_exec/exec_command.rs` and `write_stdin.rs` — exposes "start a process" and "send stdin" as two model tools, so the model can `python`, get a `>>>`, then `write_stdin` to type code. This is the **gold-standard persistent shell** for agents in 2026.

**Codex `unified_exec`（PTY + 进程注册表）**——`~/repo/codex/codex-rs/core/src/unified_exec/mod.rs:1-78` 写明模型：每次 `unified_exec` 调用要么创建一个新的 PTY-backed 进程，要么通过 id 复用已有进程句柄；输出用 head/tail 缓冲（`UNIFIED_EXEC_OUTPUT_MAX_BYTES = 1 MiB`、`DEFAULT_MAX_OUTPUT_TOKENS = 10_000`）；每会话最多 64 个并发进程（`MAX_UNIFIED_EXEC_PROCESSES = 64`，60 时警告）。handler 拆分——`tools/handlers/unified_exec/exec_command.rs` 与 `write_stdin.rs`——把"起进程"与"发 stdin"作为两个模型工具暴露，模型可以 `python`、拿到 `>>>`、再 `write_stdin` 输代码。这是 2026 年 **Agent 持久 shell 的金标准**。

**node-pty (microsoft/node-pty)** — Principle: `forkpty(3)` bindings for Node, returns a JS handle with read/write/resize. License: MIT. v1.1.0 released Dec 22 2025, 1.2.0-beta.12 Mar 12 2026 (https://www.npmjs.com/package/node-pty, https://github.com/microsoft/node-pty/releases). Used by VS Code's integrated terminal, Hyper, Theia. Strengths: stable, cross-platform (Windows ConPTY too), reference impl. Limits: native compile via node-gyp (C++ toolchain on install), version-locked to whatever VS Code uses, no Bun support — bun-pty fork exists at v1.1.3-beta.0. Adoption cost: 5-8 person-days for a Codex-style `unified_exec` clone on top. Risk: low.

**node-pty (microsoft/node-pty)**——原理：Node 的 `forkpty(3)` 绑定，返回一个 JS 句柄可读写改尺寸。许可：MIT。v1.1.0 于 2025-12-22 发布，1.2.0-beta.12 于 2026-03-12 发布。VS Code 集成终端、Hyper、Theia 在用。优点：稳定、跨平台（含 Windows ConPTY）、参考实现。缺点：通过 node-gyp 原生编译（装包要 C++ 工具链）、版本锁在 VS Code 用的版本、不原生支持 Bun——bun-pty 分支 v1.1.3-beta.0。采用成本：在它之上写一个 Codex 风格的 `unified_exec` 克隆约 5-8 人日。风险：低。

**tmux control mode (`tmux -CC`)** — Principle: line-oriented text protocol on stdin/stdout where the controller sends `tmux` commands and receives `%begin`/`%end`/`%output` events; the actual tmux server keeps panes alive even after the controller disconnects (https://github.com/tmux/tmux/wiki/Control-Mode, https://iterm2.com/documentation-tmux-integration.html). Used by iTerm2 since ~2011, by Claude Code agent-teams (cuttlesoft 2026 blog). Strengths: panes survive controller crashes, multi-window, well-tested. Limits: text protocol overhead (every byte from the guest goes through `\134`-encoding), heavier than node-pty, depends on a tmux install on the host. Adoption cost: 6-9 person-days. Risk: low-medium (the protocol is stable but parsing edge cases will bite).

**tmux control mode (`tmux -CC`)**——原理：stdin/stdout 上的行级文本协议，控制器发 `tmux` 命令并接收 `%begin`/`%end`/`%output` 事件；真正的 tmux server 即使控制器掉线也保持 pane 存活。iTerm2 自 2011 年用，Claude Code 的 agent-teams 用（cuttlesoft 2026 博客）。优点：pane 在控制器崩溃后仍存活、多窗口、久经考验。缺点：文本协议开销（每个 byte 从 guest 出来都要 `\134` 编码）、比 node-pty 重、依赖宿主装了 tmux。采用成本：6-9 人日。风险：低中（协议稳定但解析边界会咬人）。

**Other persistent-shell options (brief)**: pexpect is Python-only and out-of-scope for a TS core; libssh2 persistent channels are over-engineered for local shells; xterm.js headless adds rendering layer Quilin doesn't need; Wezterm multiplexer requires Wezterm install; GNU screen has no first-class control protocol comparable to tmux `-CC`.

**其他持久 shell 选项（简）**：pexpect 仅 Python，TS 核心用不上；libssh2 持久 channel 对本地 shell 过度工程；xterm.js headless 加了 Quilin 不需要的渲染层；Wezterm multiplexer 要求装 Wezterm；GNU screen 没有可与 tmux `-CC` 媲美的一等控制协议。

### 3. 权限模型 / Permission Model

**Claude Code 6-mode system** — Modes: `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` (https://code.claude.com/docs/en/permission-modes, https://platform.claude.com/docs/en/agent-sdk/permissions). Shift+Tab cycles, status bar shows current mode, `--permission-mode` flag persists. Evaluation flow: deny rules → ask rules → allow rules; mode applies after `allowed_tools`/`disallowed_tools`. `auto` mode (launched 2026-03-24) routes ambiguous requests to a Sonnet 4.6 classifier; `bypassPermissions` still gates a small protected-paths list. Strengths: mature UX, well-understood by users coming from Cursor / Cline; the mode-as-a-noun gives operators an obvious knob; classifier adds soft judgment. Limits: 6 modes is a lot of cognitive surface; the doc warns explicitly that `allowed_tools` does not constrain `bypassPermissions`, which is a foot-gun.

**Claude Code 6 模式系统**——模式：`default`、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions`。Shift+Tab 循环、状态栏显示当前模式、`--permission-mode` flag 持久化。评估顺序：deny 规则 → ask 规则 → allow 规则；mode 在 `allowed_tools`/`disallowed_tools` 之后生效。`auto` 模式（2026-03-24 上线）把模糊请求送到 Sonnet 4.6 分类器；`bypassPermissions` 仍然会拦截一小段受保护路径白名单。优点：UX 成熟、从 Cursor / Cline 过来的用户易上手、mode 作为名词给运维一个显眼旋钮、分类器增加软判断。缺点：6 个模式认知面太宽；文档显式警告 `allowed_tools` 不约束 `bypassPermissions`，是个 foot-gun。

**Codex execpolicy DSL** — Starlark `prefix_rule(pattern=[...], decision=...)` + `host_executable(name=..., paths=[...])` (https://github.com/openai/codex/blob/main/codex-rs/execpolicy/README.md, local `~/repo/codex/codex-rs/execpolicy/src/{policy,rule,decision,parser}.rs`). Decision values: `allow`, `prompt`, `forbidden`; load-time `match` / `not_match` examples act as inline unit tests; `decision` defaults to `allow`; effective decision is the strictest across all matches. CLI: `codex execpolicy check --rules path.rules git status`; basename fallback opt-in via `--resolve-host-executables`. Strengths: declarative, auditable, diff-friendly, examples-as-tests, can ship the same `.rules` file to all installs. Limits: prefix-rule subset only — no regex on args, no semantic reasoning ("don't `rm -rf $HOME`"); preview API may break. **This is the strongest declarative policy artifact Quilin can copy.**

**Codex execpolicy DSL**——Starlark 的 `prefix_rule(pattern=[...], decision=...)` + `host_executable(name=..., paths=[...])`。决策值：`allow`、`prompt`、`forbidden`；加载时 `match` / `not_match` 例子充当内联单测；`decision` 默认 `allow`；多条匹配时取最严格。CLI：`codex execpolicy check --rules path.rules git status`；basename fallback 通过 `--resolve-host-executables` 选入。优点：声明式、可审计、diff 友好、example-as-test、可以把同一个 `.rules` 文件发到所有安装。缺点：仅前缀规则子集——参数没正则、没语义推理（"别 `rm -rf $HOME`"）；preview API 可能 break。**这是 Quilin 最值得抄的声明式策略产物。**

**Open Policy Agent (OPA) + Rego, via opa-wasm** — Principle: general policy engine in Go; policies in Rego DSL; embeddable via `@open-policy-agent/opa-wasm` npm package (compile `.rego` → `policy.wasm`, evaluate in-process). License: Apache-2.0. 2026 status: CNCF graduated, KubeCon EU 2026 deep-dive (https://www.openpolicyagent.org/, https://github.com/open-policy-agent/npm-opa-wasm). Strengths: industry standard, supports complex deny / allow rules with structured input, fully embeddable (no sidecar), strong tooling. Limits: Rego is a non-trivial language with a learning curve; for a shell-policy use case it is overkill compared to a Starlark prefix DSL; in-process WASM eval adds ~5-15 ms latency per decision. Adoption cost: 8-12 person-days to wire and write initial policy bundle. Risk: medium (Rego literacy in Quilin team).

**Open Policy Agent (OPA) + Rego，通过 opa-wasm**——原理：Go 写的通用策略引擎；策略用 Rego DSL；通过 `@open-policy-agent/opa-wasm` npm 包可嵌（把 `.rego` 编成 `policy.wasm`、进程内求值）。许可：Apache-2.0。2026 现状：CNCF 毕业、KubeCon EU 2026 深度专题。优点：业界标准、支持基于结构化输入的复杂 deny/allow 规则、完全可嵌（无 sidecar）、工具链强。缺点：Rego 是一门有学习曲线的非平凡语言；shell-policy 用 Rego 比 Starlark 前缀 DSL 重得多；进程内 WASM eval 每次决策加 ~5-15 ms。采用成本：接线 + 初版策略 bundle 共 8-12 人日。风险：中（团队 Rego 熟练度）。

**Deno permissions** — Principle: capability flags (`--allow-read`, `--allow-net=example.com`, `--allow-run=git,bun`), all denied by default; 2026 adds `DENO_PERMISSION_BROKER_PATH` (Unix socket / named pipe to delegate decisions to an external policy daemon) and `DENO_AUDIT_PERMISSIONS` (JSONL audit log) (https://docs.deno.com/runtime/fundamentals/security/). Strengths: clean capability model, broker pattern is exactly the shape Quilin's WriteAuthority gate already aspires to. Limits: only enforced inside Deno; `--allow-run` invalidates the sandbox for any spawned child (Deno docs explicit). Not directly adoptable as Quilin runs Bun + Node, but **the broker pattern is a reusable design**.

**Deno 权限**——原理：能力 flag（`--allow-read`、`--allow-net=example.com`、`--allow-run=git,bun`），默认全拒；2026 新增 `DENO_PERMISSION_BROKER_PATH`（Unix socket / 命名管道，把决策外包给外部策略 daemon）和 `DENO_AUDIT_PERMISSIONS`（JSONL 审计日志）。优点：能力模型干净、broker 模式正是 Quilin WriteAuthority gate 想做的形状。缺点：仅在 Deno 内强制；`--allow-run` 一旦给出，所有衍生子进程就跑出沙箱（Deno 文档明说）。Quilin 跑 Bun + Node，不能直接用，但 **broker 模式是可复用的设计**。

**eBPF + Tetragon / Falco** — Principle: kernel-side eBPF programs that observe and (Tetragon) enforce policy with <1% overhead. License: Apache-2.0. 2026 status: CNCF, Cilium-graduated, KubeCon 2026 featured. Strengths: Kubernetes-native, near-zero overhead, can kill a process at syscall time. Limits: Linux only, requires kernel 5.x+, infrastructure-level (cluster admin) — overkill for a single-user CLI agent. Out of scope for Quilin's local-first shell-exec path; relevant if Quilin grows a fleet-mode server.

**eBPF + Tetragon / Falco**——原理：内核侧 eBPF 程序观察并（Tetragon）以 <1% 开销强制策略。许可：Apache-2.0。2026 现状：CNCF、Cilium 毕业、KubeCon 2026 专题。优点：Kubernetes 原生、接近零开销、可以在系统调用时刻杀进程。缺点：Linux 限定、需要 5.x+ 内核、基础设施级（集群管理员粒度）——对单用户 CLI Agent 过度。Quilin 本地优先 shell-exec 路径不适用；将来若长出 fleet-mode 服务可考虑。

**macOS TCC, AppArmor, SELinux** — Mature host-level MAC systems but they target *the entire process*, not "this one shell call." Useful as defense-in-depth (Quilin should not ship a binary that bypasses TCC) but they are not the policy layer for the agent's tool decisions.

**macOS TCC、AppArmor、SELinux**——成熟的宿主级 MAC 系统，但目标是*整个进程*，不是"这一次 shell 调用"。可作为纵深防御（Quilin 不应该发一个绕过 TCC 的二进制），但不是 Agent 工具决策的策略层。

## 推荐路径 / Recommended Path

**Sandbox: adopt `sandbox-exec` (macOS) + `bwrap` (Linux), Docker as default-off fallback. Do NOT ship gVisor or Firecracker for v1.** Quilin should follow the exact same shape as Claude Code's `SandboxManager.wrapWithSandbox` (`~/repo/claude-code/src/utils/Shell.ts:259-265`): take the resolved command string, wrap it in the platform sandbox before `spawn`, fail closed when `bwrap`/`sandbox-exec` is missing on a supported platform. Ship 3 profiles: `read-only`, `workspace-write`, `danger-full-access` — names lifted directly from Codex (https://developers.openai.com/codex/cli/reference). Vendor `bwrap` 0.11.2 like Codex does for the Ubuntu 24.04 AppArmor workaround. **Apple Container is a fast-follow** (macOS 26+ only) once it stabilizes past 1.0 — its per-container micro-VM is strictly stronger than `sandbox-exec` but ships late 2026 at earliest. Migration steps: (1) extract a `SandboxRunner` interface in `tools/sandbox.ts`; (2) add `MacosSeatbeltRunner` (sandbox-exec) and `LinuxBwrapRunner` modules behind it; (3) wire `shell-exec.ts:457` to call the runner before `execFile`; (4) write 3 profile files in `packages/agent-core/profiles/`; (5) feature-flag behind `safety.os_sandbox: "auto" | "off"` defaulting to `auto` on supported platforms. Budget: **10-14 person-days**.

**沙箱：采用 `sandbox-exec`（macOS）+ `bwrap`（Linux），Docker 作为默认关闭的兜底。v1 不要上 gVisor / Firecracker。** Quilin 应该照搬 Claude Code `SandboxManager.wrapWithSandbox`（`~/repo/claude-code/src/utils/Shell.ts:259-265`）的形状：在 `spawn` 之前把已解析的命令串包进平台沙箱、在支持平台上 `bwrap`/`sandbox-exec` 缺失时 fail closed。发 3 个 profile：`read-only`、`workspace-write`、`danger-full-access`——名字直接照 Codex 来。像 Codex 那样 vendor `bwrap` 0.11.2，绕 Ubuntu 24.04 AppArmor 坑。**Apple Container 作为 fast-follow**（仅 macOS 26+），等它过 1.0——它的"每容器一个 micro-VM"严格强于 `sandbox-exec`，但最早 2026 年底才稳定。迁移步骤：(1) 在 `tools/sandbox.ts` 抽 `SandboxRunner` 接口；(2) 加 `MacosSeatbeltRunner`（sandbox-exec）与 `LinuxBwrapRunner` 模块挂在它后面；(3) 改 `shell-exec.ts:457` 在 `execFile` 之前先走 runner；(4) 在 `packages/agent-core/profiles/` 写 3 个 profile 文件；(5) 用 `safety.os_sandbox: "auto" | "off"` 开关，默认在支持平台上 `auto`。预算：**10-14 人日**。

**Persistent shell: port the Codex `unified_exec` design directly onto `node-pty`.** Two tools: `shell_start({ command, cwd, env })` returns a `process_id`; `shell_input({ process_id, stdin, timeout_ms })` returns delta output. Match Codex's caps: 64 concurrent processes, 1 MiB output ring buffer per process with head/tail summarization at 10K tokens, warning at 60. Head-tail buffer matters: when Python prints 100 MB of progress dots, we keep the first ~5 KB and the last ~995 KB and inject `[... 99 MB truncated ...]`. Migration: (1) add dependency `node-pty@1.1.0` (or bun-pty if Quilin core moves to Bun-only); (2) new module `packages/agent-core/src/tools/builtin/unified-exec.ts` with `ProcessRegistry`; (3) keep `shell-exec.ts` as the one-shot path; (4) update sandbox runner to wrap the PTY's argv too; (5) add reaper that kills processes on session end and on memory pressure. Budget: **7-10 person-days**. Risk: native-compile pain on Windows (mitigation: build prebuilt binaries via `node-pty`'s prebuild-install).

**持久 shell：把 Codex `unified_exec` 设计直接搬到 `node-pty` 上。** 两个工具：`shell_start({ command, cwd, env })` 返回 `process_id`；`shell_input({ process_id, stdin, timeout_ms })` 返回增量输出。照 Codex 的上限：64 并发进程、每进程 1 MiB 环形输出缓冲、10K token 时做 head/tail 摘要、60 时警告。Head-tail 缓冲很重要：Python 打了 100 MB 进度点时，我们留前 ~5 KB 与后 ~995 KB，中间注入 `[... 99 MB truncated ...]`。迁移：(1) 加依赖 `node-pty@1.1.0`（若 Quilin 核心切到 Bun-only 用 bun-pty）；(2) 新模块 `packages/agent-core/src/tools/builtin/unified-exec.ts`，带 `ProcessRegistry`；(3) 保留 `shell-exec.ts` 作为一次性路径；(4) 让沙箱 runner 同时包 PTY 的 argv；(5) 加 reaper，在会话结束和内存吃紧时杀进程。预算：**7-10 人日**。风险：Windows 原生编译痛点（缓解：用 `node-pty` 的 prebuild-install 发预编译二进制）。

**Permission: add a declarative `.rules` artifact in execpolicy style, keep WriteAuthority as the runtime gate, expose 3 modes in a status bar — `ask` / `auto` / `bypass`. Do NOT clone Claude Code's 6-mode UI.** Quilin's CLAUDE.md already commits to AUTO default + CRITICAL always-asks; the implementation gap is that AUTO and the CRITICAL boundary live in TS code with no externally-auditable file. Adopt Codex's Starlark-style prefix rules as the artifact (use `@bazel/starlark` or a 200-LOC custom parser; the Starlark surface needed is tiny — `prefix_rule()` + `host_executable()`). Three modes: `ask` (every non-trivial tool prompts), `auto` (today's default; CRITICAL still asks), `bypass` (only inside `--trust auto` opt-in for idle evolution). Migration: (1) add `packages/agent-core/policies/default.rules` with ~50 prefix rules — `git status` allow, `rm -rf` forbidden, `npm install` prompt, etc.; (2) add `policy-engine.ts` that parses the rules at boot and exposes `evaluate(argv): {decision, justification}`; (3) wire WriteAuthority to consult the policy engine before its existing logic; (4) add `quilin --trust ask | auto` flag + `safety.trust_mode` config key; (5) add an audit log JSONL stream à la Deno's `DENO_AUDIT_PERMISSIONS`. Budget: **12-16 person-days**. Out of scope for v1: Rego/OPA, Sonnet-4.6-class classifier mode, Deno broker socket — revisit when policy hits 200+ rules.

**权限：增加一个 execpolicy 风格的声明式 `.rules` 产物，WriteAuthority 留作运行时 gate，在状态栏暴露 3 个模式——`ask` / `auto` / `bypass`。不要照抄 Claude Code 的 6 模式 UI。** Quilin 的 CLAUDE.md 已经承诺 AUTO 默认 + CRITICAL 永远问；实现缺口是 AUTO 与 CRITICAL 边界活在 TS 代码里，没有可外部审计的文件。把 Codex 风格的 Starlark 前缀规则作为产物（用 `@bazel/starlark` 或 200 行自写 parser；需要的 Starlark 子集很小——`prefix_rule()` + `host_executable()`）。三个模式：`ask`（每个非琐碎工具都问）、`auto`（今天的默认；CRITICAL 仍问）、`bypass`（仅在 `--trust auto` 选入下，用于 idle evolution）。迁移：(1) 加 `packages/agent-core/policies/default.rules`，里面 ~50 条前缀规则——`git status` allow、`rm -rf` forbidden、`npm install` prompt 等；(2) 加 `policy-engine.ts`，启动时 parse 规则并暴露 `evaluate(argv): {decision, justification}`；(3) 让 WriteAuthority 在自己原有逻辑前先咨询策略引擎；(4) 加 `quilin --trust ask | auto` flag 与 `safety.trust_mode` 配置 key；(5) 加 Deno `DENO_AUDIT_PERMISSIONS` 风格的 JSONL 审计日志流。预算：**12-16 人日**。v1 范围外：Rego/OPA、Sonnet-4.6 级分类器模式、Deno broker socket——策略破 200 条时再考虑。

## 迁移风险 / Migration Risks

**Cross-platform sandbox parity is the #1 risk.** Codex 0.114 → 0.130 shows that even a Rust team with a dedicated `linux-sandbox` crate burns 16 minor releases shaking out kernel-version / AppArmor / Docker-in-Docker edge cases (https://www.jdhodges.com/blog/codex-sandbox-ubuntu-24-04-fix/, codex PR #13996). Quilin must (a) keep the OS sandbox behind a feature flag for the first 4 weeks, (b) carry a vendored bwrap binary fallback, (c) log every fail-closed event with enough context to file a bug. Mitigation budget: ~3 person-days of operational engineering on top of the 10-14 day core build.

**跨平台沙箱一致性是头号风险。** Codex 0.114 → 0.130 显示：即便是带专门 `linux-sandbox` crate 的 Rust 团队，也要 16 个 minor release 才能把内核版本 / AppArmor / Docker-in-Docker 边界扫清楚。Quilin 必须 (a) 头 4 周把操作系统沙箱藏在 feature flag 后；(b) 带一个 vendored bwrap 二进制兜底；(c) 把每次 fail-closed 事件用足够上下文记录以便提 bug。缓解预算：核心 10-14 人日之外再 ~3 人日运维工程。

**Persistent-shell resource leaks are #2.** Codex caps at 64 concurrent processes (`MAX_UNIFIED_EXEC_PROCESSES`); Quilin must implement the same cap plus a per-session reaper, otherwise a model that forgets to `kill` a `python` REPL leaks file descriptors and memory across sessions. node-pty's native module has historically had crashes on Windows ConPTY edge cases — Quilin should keep the one-shot `shell-exec.ts` path as a fallback when PTY allocation fails.

**持久 shell 资源泄漏是第二名。** Codex 上限 64 并发进程（`MAX_UNIFIED_EXEC_PROCESSES`）；Quilin 必须同样设上限并加 per-session reaper，否则模型忘了 `kill` 一个 `python` REPL 就会跨会话泄漏 fd 和内存。node-pty 的原生模块历史上在 Windows ConPTY 边界有崩溃——PTY 分配失败时 Quilin 应该把 `shell-exec.ts` 一次性路径作为兜底。

**Permission-DSL adoption risk is #3.** Once a `.rules` file ships, every rule change is a versioned artifact users may have customized. Codex's prefix-rule format is preview API and explicitly may break; Quilin should snapshot Codex's grammar today, vendor it, and decouple from Codex's future breakage. Treat the rules file like a schema: bump a `policy_version` field, write a migrator.

**权限 DSL 采用风险第三名。** 一旦 `.rules` 文件发出去，每次规则改动都是用户可能自定义过的版本化产物。Codex 前缀规则格式是 preview API，明说可能 break；Quilin 应该今天 snapshot Codex 的语法、vendor 下来、与 Codex 未来的 break 解耦。把规则文件当 schema：加 `policy_version` 字段、写迁移器。

**Out-of-scope deferrals to record explicitly:** gVisor (rejection rationale: OCI-only, adds Docker tax to dev loop), Firecracker (Linux-only host, 125 ms cold start too slow), Wasmtime (only useful when workload is itself Wasm), OPA/Rego (over-engineered for v1 rule set), eBPF/Tetragon (cluster-scale, not single-user agent), Deno permission broker (Quilin is Bun+Node), Apple Container (fast-follow once 1.0 + macOS 26 adoption clears).

**显式记下的 out-of-scope：** gVisor（理由：仅 OCI，给开发循环加 Docker 税）、Firecracker（仅 Linux 宿主、125 ms 冷启动太慢）、Wasmtime（仅当 workload 本身是 Wasm 才有用）、OPA/Rego（v1 规则集用它过度）、eBPF/Tetragon（集群级，不是单用户 Agent）、Deno 权限 broker（Quilin 是 Bun+Node）、Apple Container（待 1.0 + macOS 26 普及后 fast-follow）。
