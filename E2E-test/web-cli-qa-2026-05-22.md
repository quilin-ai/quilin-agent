## 发现 / Findings

按严重级别 / Sorted by severity:

### D.1 [P1 bug] Timeline UI 显示 `writes_performed=0` 但 DB 真删 1 条
- 复现:Web "智能整理" → 真执行(delete 1 条)→ 切到 timeline tab → 显"实际写入 0 条"。
- 期望:timeline 显"实际写入 1 条"。
- 实际:`consolidation_log` 表 `writes_performed=0`。
- 根因 (suspect):Web `/api/memory/dedupe` 执行路径走 `store.delete` 但不更新 `consolidation_log` 的 `writes_performed`(plan only 用了 schema 1)。
- 证据:`sqlite3 ~/.quilin/memory.db "SELECT writes_performed FROM consolidation_log ORDER BY created_at DESC LIMIT 1;"` 返 `0`,但 `archived_at` 时间戳一致表明真 delete。

### D.2 [P1 dev experience] Turbopack 不稳定撞 stale chunks
- 复现:`pnpm dev`(默认含 `--turbopack`)→ `/memory` 报 `Cannot find module '../chunks/ssr/[turbopack]_runtime.js'`。
- 期望:dev server 启动后无 stale chunk error。
- 修复:`apps/web/package.json` dev script 去掉 `--turbopack` (commit `f877bfb`)。
- 影响:User 已 ship 修复,本测试用普通 next dev 一路 work。

### D.3 [P1 bug build error] Soul Import API 500 — module 路径解析失败
- 复现:任何 visit `/onboarding/scan` 或 `/onboarding/install`。
- 错:`Can't resolve '../../../packages/agent-core/src/config/soul-import-scanner.js'`。
- 根因:`apps/web/lib/onboarding-soul-import.ts` 用 relative path import .ts source 但 path 写 `.js` suffix(ESM convention),webpack 跨 workspace package 解析时找不到 `.js`(source 是 `.ts`)。同时 `next.config.ts` 没配 `extensionAlias`。
- 修复:`next.config.ts` 加 webpack `resolve.extensionAlias = { ".js": [".ts", ".tsx", ".js"] }`(本次会话改的,见 §F)。
- 影响:User goal 包含 Soul Import,这阻塞了整个 wizard。修复后真 scan 出 6 frameworks。

### D.4 [P0 product gap] LLM 不知道怎么选 memory tier
- 复现:dogfood 前所有 memory 都堆在 `working` tier,episodic/semantic/skill 几乎空。
- 根因:`providers/memory/src/quilin_mem/server.py` 的 `memory_store_tool` docstring 只写 'Memory tier (default "working")' 没教 LLM 选择规则。
- 修复:docstring 改成详细 tier 选择规则 + 4 个例子(commit `bc126be`)。
- 实证:修后 LLM 3/3 正确分类。

### D.5 [P2 product gap] quilin-daemon 不会自动启动
- 复现:user 装好 quilin-agent 但 KG / timeline 都不更新。
- 根因:`quilin-daemon` 默认 OFF(`QUILIN_DAEMON_ENABLED=true` 才启)+ 没在 next dev 启动时自动起。
- 建议:加 `just daemon-start-if-not-running` 或 `pnpm dev` post-hook,让 user 不用手动起。

### D.6 [P2 product gap] CLI service install 不交互

### D.17 [P1 真 bug] `/api/memory/backfill-kg` API response 谎报
- **PRE backfill:**8 edges / 3 memories
- **API call:**POST `/api/memory/backfill-kg` → 返 `{"backfilled":0, "edges":0}`

### D.18 [P0 真严重数据完整性 bug] KG triple 真重复 insert(无限膨胀)
- **复现:**反复 trigger backfill,同 `(subject, predicate, object)` triple 真在 `kg_edges` 表重复出现:
  - `孟孟 --[performed]--> QA test` × **2**
  - `孟孟 --[used]--> Playwright MCP` × **2**
  - `孟孟 --[interacted with]--> Quilin Agent` × **2**
- **根因:**`kg_edges` 表 schema 没 `UNIQUE(subject, predicate, object, memory_id)` constraint,每次 backfill 跑同 memory 真新 insert(同 LLM extract 反复跑产生同 triple)。
- **影响:**长期跑 daemon 会让 KG 表无限膨胀,user query 性能下降 + UI 重复显示同关系。
- **修建议:**`kg_edges` 加 unique constraint + 改 `INSERT OR IGNORE`,或者 backfill 前先 query 现有 triples 去重。

### D.19 [P2 suspect] incremental backfill 没真 incremental
- `KGBackfillJob.incremental=true`:理论应跳过已 process 的 memory,但 web `/api/memory/backfill-kg` 仍 process 已有 edge 的 3 个 memory(D.18 一并触发)。
- 需要看 daemon 路径是否同样问题。
